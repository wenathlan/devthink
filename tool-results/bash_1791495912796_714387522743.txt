## Operation Phases
- Fase 1: ler tudo primeiro; mapear todas as regras em um doc de regras; mapear todas as features por app em um doc de features; separar links de repos.
- Fase 2: construir os apps começando pela interface, dentro do tema.
- Fase 3: construir a lógica que vive fora do tema, na raiz.
- Fases seguintes: inventar 3-4 temas extras; cada tema novo contém SÓ pastas de página com componentes, nunca arquivos de raiz.
- Ler todos os changelogs dos repos próprios antes de qualquer coisa.
- Um app por vez (ou subagentes em paralelo enquanto o especialista faz o principal).
- Escopo: exatamente os apps listados; nenhum app extra ou externo.

## Reading Doctrine
- Ler TODOS os arquivos enviados, sem exceção, um a um, do início ao fim, a cada início e em caso de dúvida.
- Leitura por segmentos de linha (linha X a Y) direto; nunca cortar o arquivo fisicamente para ler.
- Arquivos de 22-24k linhas: leitura em blocos entre subagentes com ownership disjunto, pulando nada.
- Dedup primeiro: subagentes desduplicam arquivos de hash idêntico, mantendo a data mais recente.
- Verificar bytes reais (od/hexdump, Python/subprocess) antes de "corrigir" corrupção aparente; caches e camadas de tool podem mentir.
- Atualizar o worklog em toda Task; worklog compartilhado da família sempre atual.
- Analisar TODAS as falhas uma a uma, da mais nova para a mais antiga, sem pular nenhuma.
- Honestidade: reportar estado real, pendências e plano de continuidade; corrigir erros anteriores de verdade, nunca esconder.

## Coding Rules
- Código simples, organizado, otimizado, agrupado; direto e objetivo; JSDoc hierárquico bloco a bloco, sincronizado interna e externamente.
- 0-100 lógicas correlatas de uma responsabilidade em UM arquivo (até 300 quando a correlação exige); tudo de um contexto vive nesse arquivo, sem redundância.
- Um arquivo por contexto; lógica nunca duplicada entre arquivos; split só em concerns mistos, lógica pesada isolada, reuso necessário, ou `.ts` puro.
- Merge over split: lógicas duplicadas viram arquivo único; repetido 2+ vezes vira util/componente; cada arquivo é dono dos exports (sem barrels de re-export).
- Hierarquia ordinal dentro do arquivo: base→derivados, importante→menos importante; JSDoc em todos os blocos.
- Sincronização: blocos sincronizam entre si e com arquivos externos; interface puxa da raiz, raiz nunca puxa da interface.
- TypeScript primeiro: app nasce biblioteca multi-modo; TS ponta a ponta, JS só como emit no publish.
- Sintaxe erasável obrigatória para `.ts` rodar nativo no Node 26; proibido enum, namespace, parameter properties.
- Imports relativos SEMPRE com extensão `.ts` explícita.
- Nativo primeiro: preferir módulos built-in do Node; pacote externo só raramente e só quando nenhum nativo cobre.
- Zero JS na interface: só TS/TSX/css/html.
- Split de 2 arquivos: arquivo único quando ≤200 linhas; senão lógica `.ts` + visual `.tsx`.
- Commits pequenos: uma ação por commit, mensagem descritiva; testar antes de commitar; imitar o estilo existente.
- Try/catch rastreável embutido (error catcher para tracing posterior).
- Scripts auxiliares sempre escritos para organizar/acelerar; JS (`.js/.mjs/.cjs/.ts`) em `/tests`, não-JS em `/tests/scripts/`; nomes lowercase sem underscore/hífen.
- Formatação Biome: aspas duplas, indent 2, organizeImports; pretty, moderno, agrupado, hierárquico, sincronizado.
- Dead code com zero imports é deletado; manter integração futura válida; reativar módulos úteis desmontados.

## No-Hardcode Doctrine

## Architecture: Three Layers and Modes
- App sempre construído library-first, depois convertido a cada alvo; core library-first em TypeScript; memória interna nunca presa a um runtime.
- Layer 1 (router universal): entrada raiz importa/exporta só L2; sem L3; máx 300 lógicas correlatas por arquivo; lógica embutida, imports mínimos.
- Layer 2 (router local): cada recurso na própria pasta raiz; entrada homônima junta e exporta rotas locais.
- Layer 3 (componentes de suporte): privados; só L2 os importa.
- Interface puxa da raiz/biblioteca; raiz nunca puxa da interface; uma interface nunca puxa de outra.
- Só a lógica de entrada migra do tema para a raiz; decidir lendo interiores de arquivo, não nomes; design na raiz move para o tema, lógica fica.
- Biblioteca multi-modo: funciona como biblioteca e binário em ~30 modos, com e sem cada modo; prioridade à memória interna.
- Escolhas: buscar alternativas além do default; o mais simples, fácil e robusto; combinar opções (externo+externo, interno+externo, interno+interno) sem limite de pensamento.

## Versioning and Release
- Última casa decimal = unidades com 99 versões; chegando a 100 rola para dezenas (99 versões); chegando a 100 rola para centenas. Até 4000 features por app distribuídas em versões.
- Bump loop: qualquer bug/erro de workflow/erro de segurança → corrigir, bump da próxima versão, push, monitorar workflows, repetir até tudo verde; cada bug é um bump; registries são imutáveis.
- Release automático: manifest + CHANGELOG bump na main valida lockstep, cria a tag sozinho, constrói zips de compressão máxima + SHA256SUMS, release com notas do CHANGELOG, publica via `workflow_run`.
- Registries: npmjs, GitHub npm, Maven, NuGet, RubyGems + GHCR multi-arch; publicação idempotente com existence-check pre-deploy.
- Tags imutáveis: nunca re-tagadas; tags órfãs deletadas; runs vermelhos colaterais deletados; board 100% verde com só main.
- CHANGELOG em `.MD` maiúsculo com uma seção por versão; histórico de linhagem mesclada preservado verbatim.
- Bumps só-de-dependência commitam direto na main com PRs arquivados e branches deletados, SEM bump de versão de produto; versões de produto andam só em features.

## Verdict Engine
- Verdict julga casos ao modo Jev (estado + perguntas) sobre qualquer provider, self-hosted, com calibração pública. Verdict vive no `devthink`; entrada e gateway passam pelo `argan`; memória é N1/N2/N3; um database por pessoa. Hardcode vive SÓ no tema.
- `verdict.ts` expõe a assinatura Jev sobre QUALQUER provider via `adapters/`; trocar de provider é trocar config, zero código.
- Porter: lista ordenada de réguas resolve 80-90% a custo zero antes de qualquer chamada de modelo.
- Photocopy (cache): hash de estado+perguntas é a chave; hits retornam verdicts armazenados; nunca pagar duas vezes.
- Fan-out: disparar toda pergunta-duvida em uma trip; podar por code path.
- Semáforo de risco: verde executa, amarelo confirma, vermelho exige humano; banda cinza 0.30-0.70 nunca age; um alerta alto escala.
- Bulletin ponderado: pesos versionados combinam scores normalizados; mudar pesos, não provas.
- Cascade: baratos primeiro, verificadores estreitos por campo, modelos caros só no resíduo.
- Evidence first: extractors constroem pasta limpa antes do judge; ordem importa; overlap mantém frases inteiras.
- Guard nas duas portas: checks de input + severity score na entrada, checks de leak e ofensa na saída.
- Slice and sweep: dividir 1M em slices, julgar em paralelo, reduzir por tipo.
- Map-reduce tree: folhas julgam slices, pais resolvem conflitos até a raiz.
- Retrieve and rerank: embeddings acham top excerpts; o judge lê só esses.
- Anti-middle: reordenar a pasta por relevância antes de enviar; conteúdo importante primeiro e último.
- Pasta progressiva: leituras baratas leem índice e resumos; caras leem top excerpts completos e podem responder "nenhum se qualifica".
- Summarizer barato: mini resume cada slice; o judge lê resumos e reabre originais na dúvida.
- Memória infinita: casos vivem nos tiers N1/N2/N3; o judge busca excerpts on demand; todo fetch vira cache.
- Treino próprio: destilar verdicts rotulados com calibração como métrica de primeira classe; opção "unknown" explícita; nunca otimizar para agradar.
- Curva pública: medir erro por batch, desenhar a curva de confiabilidade no DB, aplicar temperature scaling; thresholds vêm de dados, nunca de chute.
- No-know + negação: toda escolha ganha um "nenhuma das anteriores" explícito; todo sim-não roda pergunta + negação e rebaixa altos conjuntos.
- Beam três: classificar em árvore com três caminhos paralelos; score por produto geométrico; separação sobre ganância.
- Anti-jag: contagem, matemática e datas resolvem em código antes do judge; filtrar estados gigantes; escolhas enumeradas + not-stated.
- Cost router: barato + retrieval primeiro com output "unanswerable" explícito; fallback caro só no resíduo.
- Vote DSL: regras versionadas de judge+verify+vote com quorum no DB; auditoria executável, não texto.
- Sinal sem logprobs: confiança de uma chamada a partir do trace (margin, agreement, grounding) mesmo em providers fechados.
- Hardcode só no tema: a única parte hardcoded é o design do tema chamando a biblioteca construída com config; zero branches de provider no código.
- Pipeline Nuclear-I: porter, in-guard, evidence, photocopy, fan-out, jury em cascade, weights, semaphore, out-guard, save e calibrate; fim auditável.
- Pipeline Nuclear-II: Nuclear-I + slicing, tree join, progressive evidence e distillation; qualquer tamanho, ainda auditável.
- Pipeline Nuclear-III: Nuclear-II + adapters any-provider, curva pública, consistência, beam, anti-jag, cost router, signal, votes e consumo do tema via biblioteca construída.
- Ordem de build: verdict+cache+porter; evidence+guard; jury+cascade+weights+gates; calibration+labels; slicers+memory; trainer; theme playground; testes com agreement congelado e A/B pinado.
- Verdict tests: regras a 100%; out-of-scope bloqueado; altos conjuntos nunca passam; erro dentro da tolerância do floor.
