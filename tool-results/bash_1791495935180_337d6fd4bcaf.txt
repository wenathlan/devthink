## (c) Por que o saddle standalone FUNCIONAVA e o devthink não

Diferenças concretas de padrão:

1. **Um gerenciador de pacotes por repositório vs três na família.** Saddle standalone: `npm ci` com `package-lock.json` em tudo (ci, pages, mobile, desktop, publishes) e `packageManager: npm@12.0.2`. No monorepo: devthink = bun, 7 apps = pnpm, saddle = npm, getry = bun. Todo workflow que fazia `npm ci` genérico quebra no monorepo; o pages.yml atual resolve com matrix `pm` (bun/pnpm/npm) — é o padrão correto a universalizar para mobile/desktop.

2. **Saída de build isolada vs build "em cima da raiz".** Saddle standalone: `web:build:pages` emitia em `web/dist/public` (pasta própria), e o staging era trivial (`path: web/dist/public`). Na família, o vite config de cada app declara `outDir: "."`, `emptyOutDir: false`, `assetsDir: ""` — os bundles com hash caem **junto com as fontes** na raiz do app. Por isso o seu staging por tipo é obrigatório:
```yaml
for kind in js css webmanifest xml txt svg png ico woff woff2; do
  cp *.${kind} build/pages/ 2>/dev/null || true
done
touch build/pages/.nojekyll
```
Esse é o coração da correção que você já aplicou em `pages.yml`/`mobile.yml` (`build/web`)/`desktop.yml` (`frontendDist: "../../../build/web"`) no saddle local.

3. **Capacitor config com `webDir: "."` na raiz do app.** No standalone, o capacitor.config.ts vivia em `web/` com `webDir: "."` e o workflow rodava `working-directory: web`. Na família, o config está na raiz de cada app (`saddle/capacitor.config.ts`: `appId: "com.wenathlan.saddle"`, `webDir: "."`, `android.path: "../build/native/android"`, `ios.path: "../build/native/ios"`) — **somente o saddle declara android.path/ios.path**; os demais apps (argan, cadria, etc.) não declaram, então o default seria `<app>/android` e `<app>/ios` **dentro da árvore trackeada**. Seu ajuste local resolve isso reescrevendo `webDir` no runner:
```bash
node -e '... source.replace(/webDir:\s*"[^"]*"/,`webDir: "build/web"`) ...'
```
Para a família, o mesmo step precisa também visar `android.path`/`ios.path` para `<app>/build/native/...` (ou aceitar o default e garantir gitignore), senão o `cap add` materializa wrappers dentro da pasta do app.

4. **Ícone**: standalone lia `web/icon.svg`; família tem `icon.svg` na raiz de cada app (todos exceto getry) — seu ajuste local (`icon icon.svg`) está correto; universalize lendo `src/app/icon.svg`.

5. **Deploy de pages**: standalone = 1 site com `vars.SADDLE_PAGES_BASE_PATH || base_path || /<repo>/`. Monorepo = 1 site multi-app, exigindo `VITE_BASE_PATH=/<app>/` por app (os vite configs já leem `VITE_BASE_PATH` via `pagesBasePath`/`themeBasePath` — confirmado em `argan/vite.config.ts` e `saddle/vite.config.ts`) e merge dos 10 artifacts no `assemble` — que é o que o Family Pages atual já faz.

O que vira matrix/variável:

1. **Matrix por app** (como o pages.yml atual já faz): `{ app, pm }` e, para mobile/desktop, mais: `{ app, pm, appId, appName, productName, identifier, capPaths }`. Sugestão: derivar em runtime (`node -e "require('./${app}/capacitor.config.ts')"` é TS — melhor manter a matrix declarativa no YAML, pois capacitor.config.ts não é JSON parseável direto).
2. **working-directory por app**: todos os steps de install/build/cap/tauri precisam de `working-directory: ${{ matrix.app }}` (ou `cd <app>`), incluindo o `npx cap add/sync` e o `npx --yes @tauri-apps/cli@2.11.4`.
3. **webDir/frontendDist por app**: 9 apps emitem na raiz (`.`) → staging `build/web` + reescrita do capacitor `webDir`/tauri `frontendDist` (o padrão que você já implementou). O app devthink é o desvio: seu tauri.conf.json declara `frontendDist: "build/web"` — o step de reescrita precisa tolerar/normalizar isso.
4. **android.path/ios.path do capacitor**: só o saddle declara (`../build/native/{android,ios}`). Para a família, o step de "aim the config" precisa também reescrever/injetar `android.path`/`ios.path` — ou o `cap add` vai criar `android/`/`ios/` dentro da pasta do app (choca com o structure gate de profundidade e com o gate de duplicatas).

6. **Gatilhos de path por app**: no monorepo os triggers precisam de paths `<app>/**` (o Family Pages já lista os 10); para mobile/desktop o `workflow_dispatch` precisa ganhar input `app` (choice com os 10) e o `workflow_run` precisa filtrar qual app a release afeta.
7. **beforeDevCommand por pm**: os tauri.conf.json dos apps declaram `beforeDevCommand: "pnpm dev"` (7 apps), `npm run web:dev` (saddle), `pnpm dev` (devthink app) — o scaffold do desktop reescreve `beforeDevCommand` para `npm --prefix ../../../ run web:dev`; universalizando, vira `pnpm --dir ../../../ dev` / `bun` conforme a matrix.
8. **Variáveis/segredos por app**: `vars.SADDLE_IOS_ENABLED` → `vars.<APP>_IOS_ENABLED` (ou var única de família, já que o certificado Apple é um só mas o bundle id muda — o provisioning profile é por appId, então precisa de perfil por app ou perfil wildcard); `vars.SADDLE_PAGES_BASE_PATH` → `vars.<APP>_PAGES_BASE_PATH`.
9. **getry**: fora da matrix capacitor/tauri (não tem config); entra só em pages (export estático Next) — o Family Pages atual já trata isso como leg próprio.

Steps saddle-específicos demais para universalizar sem risco:

- **O stamp inline do `build.gradle` Android** (script node que exige o template exato `versionCode 1` / `versionName "1.0"` e injeta keystore.properties + r8). Universalizável em forma, mas as mensagens/asserções estão escritas para o saddle; se o template `@capacitor/android` mudar, quebra para os 10 apps de uma vez.
- **Toda a lane `engine-validation` e `publishghcrvhe`** (Firecracker 125 ms, spoofing EPYC 9965, mesa-cache release, Dockerfile VHE, accept-key list do dockle com dezenas de chaves VHE_*) — é o motor do saddle, não da família.
- **`container-scan`/`buildextension` do security.yml do saddle** que leem `Dockerfile`/`dist/browser.js` do saddle na raiz — na família precisam de `working-directory` por app e cada app tem Dockerfile próprio (argan/cadria/debonair/devthink/saddle têm; forge/foundry/stealhead/vault/getry não).
- **`targets.yml` e `buildextension.yml`** dependem de `dist/packager/targetcli.js` e `dist/browser.js` do motor saddle — não existem nos outros apps.
- **`compatibility.yml` (root-probe)** depende de `tests/runtimeprobe.js` e `build:engine` do saddle.
