## 1. Estrutura de Arquivos e Pastas (Hierarquia Suprema)

### 1.1. Layout da raiz do repositório final (Saddle)
- **Regra 1**: A raiz exibe APENAS as pastas `docs/`, `tests/`, `web/` e `.github/workflows/` (além dos arquivos soltos da raiz). "Eu recomendo que você deixe a pasta docs, tests e web. E GitHub workflows, e aí os arquivos na raiz."
- **Regra 2**: Todos os arquivos de lógica (TS) ficam soltos na RAIZ — **sem `/src`**, **sem pasta dentro de pasta**. "Arquivos todos na raiz... lógicas pertinentes à interface da web ficam lá dentro de web, mas as lógicas gerais serão puxadas pela raiz, porque a web vai puxar da raiz, da biblioteca."
- **Regra 3**: `dist/` é artefato de build — gitignored, gerado pelos computadores do GitHub. NUNCA commitado.
- **Regra 4**: A pasta `web/` serve para: extensão, TV, aplicativo, iOS, Android, computador/desktop, tablet, deploy na Vercel e Netlify e GitHub Pages. Design universal: **nenhum arquivo duplicado dentro de web/**.
- **Regra 5**: "Uma pasta representa uma página, e lá dentro vem todos os seus componentes" — componentes em **TSX** dentro da pasta da página em `web/`; **lógicas em TS do lado de fora** (na raiz). A web importa da raiz (da biblioteca).
- **Regra 6**: Arquivos legítimos de Android/iOS só entram se NECESSÁRIO (configs específicas de Android/iOS ficam na raiz, não em pastas aninhadas).
- **Regra 7**: Pasta `.github/actions/` **PROIBIDA** — workflows 100% auto-contidos (ações compostas inlined), um arquivo por responsabilidade em `.github/workflows/`.
- **Regra 8**: `dependabot.yml` (se existir) fica em `.github/dependabot.yml`, NUNCA em `.github/workflows/` (GitHub o parseia como workflow e falha).
- **Regra 9**: Scripts externos (.mjs/.py/.sh de apoio) em `scripts/` quando existirem; nada de .mjs/.cjs soltos na raiz (viram TS ou build).

### 1.2. Mesclagem de arquivos equivalentes
- **Regra 10**: Arquivos com nome equivalente entre repositórios são **mesclados num só arquivo** — ex.: dois `.xml` viram um; `app.tsx` + `app.tsx` = um `app.tsx` com todas as features; `index.html` + `index.html` = um com tudo. **Sem excluir as features de ambos.**
- **Regra 11**: **Nenhuma feature, arquivo ou doc é perdido** de nenhum dos dois repositórios. Ctrl+X/Ctrl+V mental: tudo do repo mesclado vai para as pastas equivalentes do produto final, renomeando para não sobrescrever, depois ajustando e mesclando.
- **Regra 12**: Metadados do repositório mesclado **viram o produto final**: tudo que era "e2ugh" (E2ugh.java, e2ugh.csproj, e2ugh.gemspec, E2UGH_DB, labels, nomes de pacote) é **readaptado para Saddle** (Saddle.java, saddle.csproj, saddle.gemspec, SADDLE_DB etc.). Na publicação, todos os metadados vão para o Saddle. Binário ÚNICO no package.json (a CLI do mesclado vira comando da CLI do produto final).
- **Regra 13**: Lógicas correlatas (de 0 a 100) de mesma responsabilidade ficam em **UM só arquivo** — ex.: Dockerfile cuida de TODA a configuração de container; **NÃO pode existir** `docker-compose.yml`, `Dockerfile.full`, etc. "O Dockerfile vai cuidar da configuração de todo o container... é o único arquivo que vai cuidar do contexto de container."
- **Regra 14**: Um arquivo = uma responsabilidade; dentro dele, organização hierárquica, ordinal e agrupada (do mais importante ao menos importante, da base aos derivados), com JSDoc em todos os blocos.
- **Regra 15**: Zero duplicação de conteúdo entre arquivos (verificação pairwise); zero clonagem interna; versões stale confinadas ao histórico (CHANGELOG).

### 1.3. Nomenclatura
- **Regra 16**: Nomes de arquivos 100% **minúsculos, sem hífen, sem underscore** — apenas pontos ou tudo junto. Exceções essenciais da raiz: `Dockerfile`, `LICENSE`, `package-lock.json`, `CHANGELOG.md`, `SECURITY.md`, `README.md`/`readme.md` (o CHANGELOG/README em MAIÚSCULO .MD é o padrão família — "o chancelog não tá em maiúsculo" foi repreensão).
- **Regra 17**: Nomes de variáveis/identificadores/chaves JSON em **camelCase** (sem underscore/hífen). Código, comentários e docs em **inglês**.
- **Regra 18**: Zero emoji no código/documentação.

## 2. Hashes, Checksums e Artefatos de Build

- **Regra 19 (Doutrina Central)**: **NENHUM hash SHA-256/criptográfico hardcodeado** em workflows, Dockerfile ou arquivos da raiz. "Os hashes vão ficar para os computadores do GitHub... e colocados nos artefatos lá em assets, no release, no release notes."
- **Regra 20**: Actions do GitHub referenciadas por **TAG de versão** (`@vX.Y.Z`), nunca SHA-40. Imagens base por **tag** (`FROM node:26-slim`), nunca `@sha256:` digest (digest único não serve multi-arch).
- **Regra 21**: SHA256SUMS gerado no runner como asset da release; digest de assets resolvido em runtime via API do GitHub (os computadores do GitHub computam os hashes).
- **Regra 22**: **Builds e testes acontecem nos computadores do GitHub** (workflows) — o agente NÃO gera binários, NÃO roda a bateria de testes autoritativa, NÃO salva assets na raiz. "Quem vai cuidar dessa parte do build, de gerar os artefatos, os binários, vai ser os computadores do GitHub."
- **Regra 23**: **PROIBIDO na raiz**: `.apk`, app, `.ipa`, container buildado, `__pycache__` (pycache devia estar oculto/gitignored — "não vai estar presente na raiz"), `dist/`, `node_modules/`, zips/rars. "Nunca commitar zips" — o build pesado (QEMU/container) é do GitHub.
- **Regra 24**: Alertas Scorecard PinnedDependencies → dismissal "won't fix" com política do mantenedor (tag de versão é o contrato), limite 280 chars, como iakadion.
- **Regra 25**: Vulnerabilidades resolvidas NA RAIZ com `overrides` no package.json — sem arquivos de ignore (.trivyignore, osv-scanner.toml — não existem na família).
