# Devthink 1.1.1 Extension Architecture

Devthink 1.1.1 is a browser-extension package, not a hosted control platform. The repository exposes a reusable TypeScript library and one Manifest V3 Chromium target. It does not copy code, trademarks, user interface, proprietary protocol or branding from the public products reviewed during research.

## Product boundary

The extension is a user-controlled tool bridge. It may observe an approved active tab and prepare a typed action proposal for a configured agent endpoint. It never grants blanket browser access, reads cookies, uses the Chrome debugger API, installs native software, bypasses a CAPTCHA, works around login controls, or executes a browser action without the user selecting a reviewed proposal.

Browser extension service workers are event driven and not a reliable 24-hour compute environment. A future always-on agent must be a separately installed or hosted process with its own configuration, consent screen, operational monitoring and release review. The 1.1.1 extension remains a session-scoped bridge.

## Three-layer message flow

| Layer | Component | Trust boundary | Function |
| --- | --- | --- | --- |
| User surface | Popup and side panel | Direct user input | Configure a secure endpoint, choose a tab, inspect proposal, approve, reject, stop and view audit events. |
| Extension broker | Background service worker | Manifest capability boundary | Maintains session state, validates messages, injects the active-tab observer, requests optional origin access and relays approved requests. |
| Page bridge | One-time active-tab script | Approved page boundary | Returns an accessibility-oriented snapshot and performs a narrowly scoped, explicitly approved DOM action. |

The optional remote endpoint is not a command authority. It may submit a typed plan proposal only after the user has configured a HTTPS origin and granted that exact optional host permission. The background broker rejects commands with an unknown session, an origin mismatch, expired approval, unsafe action class or unsupported schema version.

## Deliberate exclusions

The research found that broad browser permissions are common. They are not a requirement for Devthink. Version 1.1.1 excludes `debugger`, `cookies`, `webRequest`, `history`, `bookmarks`, `downloads`, proxy modification, broad host access, native messaging, secret scraping, CAPTCHA solving, automatic credential handling and remote code execution.

## Target resolution grammar since 1.1.33

Every page step may address its element through a reviewed `targetref` in the step `options` instead of, or beside, a css selector target. The page bridge resolves the reference against the live dom in one pass at preview time and again at execution time.

| Mode | Reviewed fields | Resolution behavior |
| --- | --- | --- |
| `selector` | `selector` | A css selector resolved against the document; the default mode of a plain step target. |
| `text` | `text` | Matches the visible own text or accessible label of every element; exact matches win over substring matches. |
| `aria` | `role` plus `name` | Matches the aria role (explicit or implicit) together with the accessible name. |
| `name` | `name` | Matches the accessible name alone, preferring the single clickable element when several share one name. |
| `xpath` | `xpath` | Evaluates the supported xpath subset (tag or wildcard steps, attribute, text and positional predicates) against a serializable node tree. |
| `index` | `index` | A one based clickable map number, stable inside one observation version. |
| `point` | `x` and `y` | Viewport coordinates resolved through the element under the point. |

Zero matches are reported as absent, exactly one match resolves and returns a `resolvedtarget` summary (mode, selector, tag, label and geometry) that is attached to step results and review envelopes, and two or more matches are refused as ambiguous with a candidate list so the user can choose. `clickpoint`, `clicktext`, `clickaria`, `clickname` and `resolvexpath` are convenience kinds bound to one mode each.

## Observation pipeline and watch lifetimes since 1.1.34

The reviewed vocabulary grows to one hundred eighteen kinds, and the twenty eight new ones are all read only observers graded by an observation mode: `passive` kinds capture one state, `watching` kinds observe across a reviewed lifetime window, and `diffing` kinds compare two stored observation versions. The pipeline is one flow: the background gate checks the session, the approved plan and (for `readjson`) the session origin grants, dispatches the step through the page bridge, stores the structured evidence, refreshes the live page signals (language, template, scroll lock and banner state) and streams everything back into the step result, the context payload and the review surfaces.

| --- | --- | --- | --- |

## Extraction pipeline and artifact store since 1.1.38

The forms and data part two family turns reviewed pages into structured datasets: `scrapetable` and `paginateextract` dispatch through the page bridge, where `extension/pagedata.ts` normalizes header cells into stable slugified column keys with unique suffixes, expands rowspan and colspan cells into filled rectangular grids, separates nested tables into child datasets linked to their parent rows, resolves the next pagination control from numbered page entries and waits for fresh rows between page turns; `extension/datacommand.ts` holds the background logics (dataset records, artifact exports with checksums, chunk planning with backpressure, cursor advancement, loop row variables, provenance records and artifact retention), and `extension/background.ts` keeps the executors, the persistence and the audits with the five new audit kinds (scrape, export, stream, resume, provenance). `extension/pagebridge.ts` keeps the dispatch seam.

Exports are consent gated twice: every kind that moves data out of local memory is sensitive and refuses to run while the session origin grants do not cover the active origin, sheet pushes additionally need a configured HTTPS endpoint behind its optional origin permission plus the explicit reviewed flag, and the clipboard copy negotiates the optional clipboardWrite capability. Artifacts land in the task artifact store with a deterministic checksum and a provenance record per export that keeps the source url, step ref and row range, so every exported row stays auditable end to end; artifact retention is a user setting and an absent setting keeps every artifact.

Streaming and resume guarantees: `streamdisk` splits the dataset into reviewed chunks with no code ceiling on the chunk size, writes them sequentially with backpressure (the writer never keeps more than one unacknowledged chunk in flight), persists the stream state after every acknowledged chunk so an interrupted stream resumes from the stored counters after a service worker restart, and lands the completed artifact in the store at the end; extraction sessions persist their cursor and page history the same way, so `resumeextract` continues an interrupted extraction from the stored cursor by stepping the reviewed next control forward.

## Acceptance criteria

1. The default manifest asks only for `activeTab`, `storage`, `scripting` and `sidePanel`.
2. A server origin remains blank until entered by the user and is granted with an optional-host-permission prompt.
3. A browser action requires an active user session, same-origin target, valid plan identifier and an explicit approval record.
4. Every request, decision and result creates a local audit event.
5. The package builds a loadable unpacked extension and a library archive at version 1.1.1.
6. Unit tests demonstrate that policy rejection occurs before page-bridge invocation.

The native host bridge lives in two pure modules beside the companion sources: `nativehost.ts` holds the host manifest template with its generated extension id placeholder, the installer and uninstaller behind the install consent (both with injected filesystem seams), the runtime port states with the crash and reattach path, the companion handshake with the one major version upgrade window, the capability negotiation, the native surfaces, the correlation ids, the heartbeat liveness, the frame checks, the secret exclusion, the rate cap accounting, the audit records and the diagnostics; `wsbridge.ts` holds the localhost bind checks, the per session tokens with their hash-only records, the frame authentication, the one extension connection rule, the idle expiry and the servercontract envelope translation. The companion process ships as the one `companion.ts` source module — it speaks the length prefixed json wire, hosts the wsbridge websocket server, exposes the desktop surfaces behind consent and embeds the host manifest template the build stamps — and the background wires the family through the native command executor (the chrome runtime port seam injects the native messaging port) while the options page renders the install state, the consents and the diagnostics.

## Cross browser polyfill layer (1.1.86)

The cross browser build removes the chromium only assumption in packaging. Three pure modules live beside the native bridge: `apimap.ts` records every webextension api the codebase touches with its chromium, firefox and safari equivalent, resolves the right call through a runtime browser probe (the in memory cache holds the resolved browser for the run) and reports the unmapped apis at build time so a new api without a row fails the build before the cross browser artifacts ship; `browserpolyfills.ts` builds the polyfill layer for one runtime — prefers the `browser` namespace when present (firefox and safari) and falls back to the `chrome` namespace (chromium), wraps the callback style the older engines speak into the promise shape the reviewed vocabulary reads, and ships the per surface normalizers (sidepanel with the popup window fallback, scripting with the tabs.executeScript fallback, storage with the local and session area keys, tabs and windows with the query, create, update and bounds handling, notifications and contextmenu with the options and item creation, clipboard, downloads, runtime messaging and geturl); `firefoxprep.ts` adapts the source manifest for firefox (layers the browser specific settings with the generated extension id, the strict min version, the action key mapping, the event page background scripts, the optional permission names that differ, the empty host permissions the deny by default posture keeps, the deny list in force across overlays and the web accessible resources firefox pattern syntax, and strips the `browsers` and `vsix` metadata keys from the adapted manifest so the shipped firefox extension copy carries no packaging metadata); `xpipack.ts` assembles the firefox build into a zip ready for signing with the manifest placement at the archive root, the hashed assets beside it and the artifact name that carries the release version; `safariskeleton.ts` generates the xcode project wrapper that embeds the chromium build as the safari web extension payload, declares the app entitlements for the extension distribution and includes the minimal app shell that opens the extension. The per browser overlays live inside the root `manifest.json` under the `browsers` key (`browsers.firefox` and `browsers.safari`) and the build keeps that single root manifest as the one source manifest — the overlays layer on top of it inside the same file, never as separate hand maintained manifests.

## The frozen message boundaries since 1.1.91

The 1.1.91 api freeze pins the message boundaries the three-layer flow crosses: every message type the background router dispatches, every member the injected pagebridge exposes, every kind the sidepanel and popup helpers send, every command the cli dispatches, every symbol the library exports and every tool the mcp catalog serves — all frozen in the capability manifests the build emits under `dist/caps/`. A surface change without its manifest update never ships, because the apifreeze gate hashes every frozen list and refuses a changed hash without a release bump.

The boundaries follow the frozen contracts: the request router speaks the two hundred thirty four background message types the background manifest lists (the capmanifest message answers the served manifest beside the negotiated protocol version), the page bridge answers the thirty one devthinkbridge members the pagebridge manifest lists, the panels speak the message kinds their manifests list against the same router, and every inbound message runs schema validation before dispatch — strict mode for protocol version two refuses unknown fields while a version one client keeps the tolerant deprecation window that closes at 2.0.0. The versioned envelope travels the frozen carriers the message catalog names, the response envelope covers the success, error and cancel outcomes, and the protocol major negotiation answers two to a new client, one with the deprecation notice, and a refusal with the supported range above two. See `docs/apifreeze.md`, `docs/stability.md` and `docs/deprecation.md` for the full freeze rules.
