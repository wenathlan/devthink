# Gateway guide (1.1.83)

The gateway integration guide is the entry point for every model provider surface: how the provider adapters speak, how the base url and the key vault configure, how routing picks a provider, what consent a gateway call needs, which bounds stay user choices, and how the token budgets and the cost tracking reconcile. The roadmap wrote this guide as docs/15.gatewayguide.md; slot 15 belongs to the consent model of the 1.1.61 family (docs/15.consentmodel.md), so the guide takes slot 24. The narrative here links the detail documents rather than duplicating them: the options page settings live in [configuration.md](configuration.md), the user guide of the model surface in [llmguide.md](llmguide.md), the protocol surface the tools advertise through in [agentprotocol.md](agentprotocol.md), the accounting certification in [costcert.md](costcert.md) and the dispatch loop arithmetic in [05.agentalgorithms.md](05.agentalgorithms.md).

## the provider adapters

Four adapters ship, and every one implements the same contract — build one wire request, parse one answer body, parse one streamed body into ordered tokens, list the models the endpoint offers, serialize the tool catalog in the provider's own schema:

| Adapter | Request shape | Stream shape | Tool schema | Default base url |
| --- | --- | --- | --- | --- |
| `openaicompat` | the chat completions shape, `POST /chat/completions` | server sent event deltas | the function tool schema | none — any compatible endpoint the user configures |
| `anthropicgateway` | the messages shape with the system prompt mapped to the top level system field | content block deltas | the input schema format | none |
| `geminigateway` | the generate content shape, the model rides the path | candidate parts | the function declarations format | none |
| `ollamalocal` | its own localhost wire format | message lines | its own serialization | `http://localhost:11434`, the loopback machine only |

The dispatch loop wraps every adapter with one request, stream and cancel contract: the consent and base url gates run first, the timeout races the call, transient failures retry under the jittered backoff, the `retry-after` header of a 429 answer is honored with its announced window, the 401 and 403 answers map to the unauthorized error the vault rotation answers, and the cancel state stops before the dispatch and between the attempts. The `capabilityad` advertisement serializes the tool catalog into the provider specific schema with the consent metadata and the plan review gate riding the required capabilities — a model answer never executes a step the human review did not approve, because the tools it sees carry the same consent line the mcp catalog carries. The `modellist` discovery parses the endpoint's model list into ids, labels, context window and modality hints, and caches under the user configured window.

## base url and key vault configuration

Each provider names its kind (`openaicompat`, `anthropicgateway`, `geminigateway` or `ollamalocal`), its base url, an optional path prefix that sits between the base and the wire path, its model list and its api key reference. The `baseurlconfig` validation refuses a query or a fragment, refuses a relative path segment, requires https for every remote provider and accepts localhost hosts only for `ollamalocal` — so no provider endpoint is contacted unless the user configured one, and the ollamalocal adapter alone carries a default (the loopback machine, never a cloud url).

The key material lives in the keyvault behind its storage id — never in memory files, audit trails or request logs. The vault seams (`storeproviderkey`, `resolveproviderkey`, `revokeproviderkey`) are the only paths a value takes: the key resolves at the last possible moment before the wire, `maskkey` and `maskrequest` mask every request before any log, and the key export check refuses any export that carries a key shape. Every provider ships off until the user turns it on, and the options page holds every setting (see [configuration.md](configuration.md)).

## routing

Model routing maps task kinds onto provider and model pairs with the fallback pair beside every route: the internal task kinds are `parsecommand`, `classifyintent`, `draftplan`, `replan`, `reflect` and `summarize`, and the user may route any further task kind. The `resolvegatewayroute` resolution answers its source — `route`, `fallback` or `local`: a failing primary provider marks itself unavailable and the fallback takes over, both failing asks the user because no default route ever applies, and the local provider stands in when the consent gates refuse the remote calls. The resolution honors the remote allowed flag and the session origin, route edits bump a revision that persists into the routing history, and the routing costs land on the right agent with every cost line carrying its routed provider and model (the reconciliation lives in [costcert.md](costcert.md)).

## consent for gateway calls

The consent gate asks the user before the first call to any remote provider, while the local runtime needs no remote consent. Every provider call grades as a data egress event: the audit entry names the endpoint, the model and the token counts, and page content never joins a call the user has not granted. The tool catalog the advertisement carries ends with the consent line every model reads — tools with side effects execute only the approved plan step they name — so the model sees the boundary it operates inside. The full consent model behind the gates is [15.consentmodel.md](15.consentmodel.md).

## timeouts, retries and the guardrails

Every timeout, retry count, backoff base, jitter window and model list cache window stays a user choice with no engine default. The guardrails wrap every parsed response: `stripguardrails` opens code fences and cuts the chatter around the json object, `parseoutput` validates the stripped text against the expected schema, the `gatewayguard` caps the parse attempts with its retry prompt naming exactly what the retry asks, and a response that never parses answers the structured gateway error instead of leaking through. The honest limitation stands from [llmguide.md](llmguide.md): the extension runs in the browser, so provider calls ride the ambient fetch of the extension context and every remote endpoint must be reachable from it — the local endpoint keeps sensitive work on the machine.

## the openaicompat endpoint landscape

Nothing is hardcoded: no provider allowlist exists, no built-in provider name ships, and no endpoint or model default applies — the openaicompat adapter works with any compatible endpoint the user configures that speaks the chat completions shape, and the endpoint landscape is the user's own. The protocol styles are wire shapes the user picks for interoperability, not providers; the key placement follows the shape the endpoint speaks — `Authorization: Bearer` for the chat completions and responses shapes, the `x-api-key` header for the messages shape and the `?key=` url parameter for the gemini shape — and optional extra headers serve the gateways that need them. The full shape table and the prompt library beside it live in [llmguide.md](llmguide.md).

## local model usage

The local model endpoint is a first class citizen. The `ollamalocal` adapter speaks to a localhost endpoint that defaults to `http://localhost:11434` and never to a cloud url; a `localmodelconfig` names a loopback endpoint (localhost, 127.0.0.1, ::1 or a .localhost host), the model and its shape; every call to it stays on the machine, the usage records carry the local marker for the calls that never left the machine, and policy grades local endpoints as the preferred surface for sensitive extractions. The health check button sends one ready prompt and stores the result.

## token budgets and cost tracking

The usage record of every gateway call carries the prompt, completion and total tokens, the optional cost estimate answering the user configured price per million tokens, the provider, the model, the endpoint, the request id and the run, step and session ids it belongs to. The cost budget holds optional token and currency ceilings per run: the budget check halts the run and asks the user when a ceiling reaches (an absent ceiling stays the documented unbounded choice), the budget meter shows the accumulated tokens and the recorded cost of every model call against the configured ceiling, and `getusage` answers token and cost totals per run, per step and per period. The costcert gate reconciles the whole accounting by replay and recompute — the token lines recompute, the per agent accounting matches the step logs, the refunds on cancelled steps bill only the chunks that left the wire, the exported cost report reparses with the same numbers and no cost event is missing from the audit trail (the full method is [costcert.md](costcert.md)). The multi agent layer folds the same accounting through the shared ledger, so the panel and the certification read one set of numbers.
