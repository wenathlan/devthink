# Consent model

Devthink 1.1.61 hardens the trust boundary itself. The consent gates do not move: every security operation rides the same session, plan and origin review, no security record ever bypasses the human review, and no duration, boundary, shape list or kind list is ever hardcoded — they are user choices.

## The denydefault posture

The documented posture refuses every origin the user never granted. The per origin automation allowlist holds one exact origin per entry with no wildcard expansion — a star, an empty segment or a scheme wildcard never covers any origin and a wildcard entry refuses the whole check. The active tab grant counts as exactly one explicit single origin grant, and the allowlist scopes per profile workspace so parallel profiles never share grants. The executor checks the allowlist before every dispatch and records an allowlist miss as a denied event without navigation; the popup shows the allowlist state of the active tab and requests a grant when a task targets a new origin.

## Origin profiles

`originpolicy.ts` holds the per site grammar: `originprofileof` builds one profile per origin, `profilekind` moves an action kind between its grants and its denials so the lists never overlap, and the policy consults the profile before every sensitive kind through `originprofilegate`. An explicit denial refuses the kind on that origin, an explicit grant allows it while the fresh class consent gate still routes the sensitive classes through their prompts, and an absent profile leaves the decision to the class consent gate alone.

## Consent windows

Every sensitive grant binds in time. `openconsentwindow` opens a window scoped to exactly one session and one origin with the duration the user chose — the prompt always names a boundary and never defaults to unlimited. `consentwindowstate` reads the remaining time, `windowgatesstep` expires the window at its duration boundary and suspends the run mid step, the executor refuses to resume a session whose window has expired, and `renewconsentwindow` renews only through a new explicit prompt that opens a brand new window while the old one stays closed in the history. Memory expires closed windows past their boundary while the records survive for the audit trail. The sidepanel shows the remaining consentwindow time per active run with a renew action, and options document that grants never outlive their named boundary.

## Sensitive classes

`type sensitiveclass = "payment" | "credential" | "delete" | "publish"`. The classifier names the class from the kind table (card fills are payment, password consent, api key saves and auth flows are credential, discards, pattern closes, cookie clears and cleanups are delete, posts, messages, submits and clipboard writes are publish) and refines it by the kind options rather than the kind names alone: a form submit carrying card field shapes grades payment, a submit bearing password or token shapes grades credential, and a mutating rest or graphql call grades publish while its read verbs stay plain. Uploads, downloads and evaluate grade sensitive by default without a named class, so their fresh consent rides the consent window prompt itself. Each class needs one fresh consent prompt per origin through `classconsentcovers` and `missingclassconsents`; the prompt of one class never widens another. The sidepanel renders sensitive steps with their class badge and the popup shows the originprofile summary beside the denydefault notice.

## revokerun

The mid run revocation is a terminal session event. `revokerun` halts the pending step and every queued step without executing them, `revokerungate` accepts the event as terminal so no later step of the revoked run dispatches, and the rollback list `haltedstepsof` names the halted steps the sidepanel confirm dialog shows before the user confirms. The revocation writes a terminal immutablelog entry naming the user action, the progress log records the run as halted with the revoked step, and the memory keeps the revocation history visible so later consent prompts can read it.

## The immutable log and its loghash chain

Every step transition, grant, expiry, revoke, deny, suspension and resume event lands in one append only log per session. `logentryof` derives the entry hash at append time — the sha-256 over the predecessor hash and the canonical entry body — so `loghash` carries the previous hash, the entry hash and the algorithm. There is no update or delete path: a sealed log refuses every append, and `sealrunlog` closes the log at session completion with a final hash chained to the last entry. `verifylogchain` re-derives every link at read time and reports the broken entry as tamper evidence; the audit accessor serves log reads only through this verification and refuses a chain with a broken link entirely (`logreadgate`), and `exportlogchain` exports the verified chain as an audit file the options surface offers. Honest limit: the browser storage areas offer no append only hardware, so the log derives its integrity from the hash chain that makes any rewrite detectable at read time; the memory adapter seam documents the future append only backend.

## maskinputs

Typed secrets never reach a record. The recognizer reads the documented password, token, card and secret field shapes and the user extends them through the global `maskshapes` setting and the per origin mask rules (`shapesof`). `masktypedvalues` masks the typed value and the option payload of a step before they reach the log writer, `maskformstate` and `maskobservation` keep the observation field shapes while the values behind masked shapes carry the `[redacted]` marker, `maskstoredvalues` covers stored values, and `maskexport` excludes masked values from every export of the run record. The page bridge masks typed values and form state at its boundary, the background masks outcome details before persistence, and the sidepanel shows masked values as redacted fields in the step details.

## Security part two (1.1.62)

The protections for secrets, messages and money ride the same review chain. The secretvault keeps values behind its seam — `vaultstore`, `vaultvaluefor` and `vaultdelete` are the only paths a value takes, the persisted records carry labels, scopes, provenance and digests only, the leak scan refuses a plan text, variable or step option whose value digests to a vault record, and `secretshapecarrying` refuses a raw typed value behind a masked field shape. redactshots mask the sensitive regions of every capture kind before storage. schemastrict, origincheck and connectallow guard every inbound command, message and port: unknown senders drop without handler execution and the connectallow list ships empty by default. ratelimit buckets bound automation per origin and per session by deferring until the window resets. confirmpay, confirmdelete and confirmcreds hold payments, destructive deletions and credential use in front of one distinct human action each — no timeout resolves a gate and no batch approval resolves two; the gate waits record beside the step durations in the progress log. phishguard blocks login origins whose lookalike distance to a granted origin crosses the user threshold and names the matched origin in the deny event. safedefaults profile an origin without an originprofile as reads only with every sensitive class denied; the popup notice links to the originprofile editor because only the user widens the profile. The immutable log gains the gate, phish, schema and inbound event kinds, and the transparencypage serves every grant, window, sender, permdiff and vault label in one read with a revoke action beside every listed grant.
