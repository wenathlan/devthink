# Extension Permissions Evidence

## Purpose

This record captures the first public evidence used to define Devthink's browser connector. It distinguishes published product claims from platform guarantees. The product must not claim capabilities beyond the sources or the implemented tests.

## Evidence Matrix

| ID | Source | Verified statement | Design implication |
|---|---|---|---|
| EP01 | Manus AI Browser Operator listing | The listing describes agent access to a user-authorized, specific tab and says the user can stop activity by closing that tab. | Devthink will use an explicit session scope, present an active-session indicator, and provide a direct stop action rather than universal unattended browser control. |
| EP02 | Chrome extension permissions documentation | Chrome distinguishes install-time, optional API, host, and optional host permissions. Optional permissions can be requested at runtime and improve informed user control where functionality permits. | The connector will keep a minimal base manifest and request site access only during explicit pairing or scoped consent. |
| EP03 | Manifest V3 overview | Manifest V3 uses service workers and prohibits remotely hosted executable code in extensions. | The extension will package executable code in the signed artifact; server-delivered configuration must be declarative and schema-validated. |
| EP04 | MDN optional permissions documentation | Firefox supports runtime permission requests, permission inspection, and revocation observation; optional host permissions are the preferred MV3 form for optional hosts. | The browser adapter will expose permission state and revocation events through a common typed contract, with browser-specific implementation details isolated. |

## Initial Permission Baseline

The initial non-destructive connector will request only storage, active-tab access on a user gesture, and optional host permission for a site selected in an explicit pairing flow. It will not request access to browsing history, cookies, all tabs, debugger APIs, or broad host patterns in the first release. Each elevated capability must show a human-readable reason, be time-bound or session-bound where the browser allows it, and be logged as an audit event.

## Optional Capability Model since 1.1.32

The required permission set stays locked to `activeTab`, `storage`, `scripting` and `sidePanel`; nothing privileged is installed by default. The manifest now declares `tabs`, `downloads`, `clipboardRead` and `clipboardWrite` as optional permissions, following EP02 and EP04: each capability is requested at runtime from the review panel, only when a reviewed step needs it, and every grant or refusal is audited. Browser-level action kinds check their capability before execution: `tablist` requires `tabs` and `downloadfile` requires `downloads`; other tab and window operations run on the granted active tab without extra permissions. The CLI manifest gate keeps the required list locked and validates the optional list against this model. The forbidden set (debugger, cookies, webRequest, history, bookmarks, nativeMessaging, proxy, management) remains forbidden in both lists; capability growth removes arbitrary limits, never consent gates.

## Tabs and windows capability model since 1.1.36

The 1.1.36 tabs and windows command family runs on the same optional `tabs` capability the earlier tab kinds already negotiate: every one of the thirty two new kinds checks `requiredcapability` before execution, the review panel can request the grant, and every grant or refusal is audited. Two capability boundaries are documented deliberately.

Tab groups: the manifest excludes the Chromium `tabGroups` permission, so `grouptabs`, `colorgroup` and `collapsegroup` keep membership, colors and collapse states inside the Devthink group registry persisted in local storage. Group steps move their member tabs through the tabs api and re-derive registry order from the live tab set, but they never call the native group api; the review panel renders the registry, and the exclusion keeps the install-time permission list unchanged.

Incognito windows: `incognitowindow` creates a private window only on the explicit reviewed request, requires the user to allow the extension in incognito mode, and the resulting window profile never inherits the session origin grants — `windowprofilegrants` refuses grant inheritance for incognito while normal and scratch windows keep it. The same separation keeps the private containers of 1.1.35 outside the session grant chain.

## Form profile storage and password consent since 1.1.37

The 1.1.37 forms and data family adds no permission at all: every form kind runs inside the already granted `activeTab`, `storage` and `scripting` surface, profiles, tickets, wizard states, error reports, captcha handoffs and detections live in local extension storage, and the manifest permission lists stay byte identical to 1.1.36.

Form profile storage is consent bounded twice: `saveprofiles` stores a profile only behind the session origin grants captured at save time (the grants list is part of the stored profile), and applying a profile rechecks `profilegrantgranted` so a profile saved for one origin never fills a page of an ungranted origin. Password entries are refused inside form records and saved profiles outright — the only path to a password field is the explicit `consentpassword` kind with a reviewed consent ref, whose audit line records the ref and never the value.

Generated values are bounded by the same honesty rule: `generatevalues` refuses to emit values that look like real card numbers or personal identifiers (a Luhn valid thirteen to nineteen digit run outside the 4111 test prefix, or the dashed identifier shape), so generated card data is always test prefixed. The one time code entry stays behind the consent gate of an active session: the reviewed code is stored locally only while a session is live, and the `fillcode` page filler waits for the reviewed source before typing. Captcha presence never forces a solve — `handoffcaptcha` records the handoff, pauses the plan and hands control back to the user, who resolves it from the review panel.

## Sheet endpoints and artifact exports since 1.1.38

Data exports never leave local memory silently: `exportcsv`, `exportjson`, `exportexcel`, `copytable`, `pushsheets` and `streamdisk` are all sensitive kinds, and each refuses to run while the session origin grants do not cover the active origin. Disk artifacts stay inside the task artifact store with a deterministic checksum and a provenance record per export (source url, step ref, row range), the clipboard copy requires the optional clipboardWrite capability, and artifact retention is a user setting with no code ceiling.

Sheet pushes are locked behind three explicit reviews: the HTTPS endpoint must be configured from the review panel (stored as a sheet endpoint config), its origin must hold the optional host permission, and the step itself must carry the explicit reviewed flag. The manifest gains no new permission for any of this — required permissions stay `activeTab`, `storage`, `scripting` and `sidePanel`, and optional permissions stay `tabs`, `downloads`, `clipboardRead` and `clipboardWrite`.

## Initial Consent Baseline

The dashboard will generate a plan first. The user can inspect the target site, intended observations, action classes, timeout, checkpoints, and approval requirements before an execution request can be sent. Any action classified as sensitive, destructive, external communication, or unapproved will remain blocked until a separate explicit approval is recorded. Revocation and emergency stop are higher-priority transitions than in-progress execution.

## Downloads, clipboard and scanning since 1.1.39

The 1.1.39 files, clipboard and downloads family adds no permission at all: every kind runs inside the already granted `activeTab`, `storage` and `scripting` surface, the downloads and clipboard kinds negotiate the existing optional `downloads`, `clipboardRead` and `clipboardWrite` permissions on demand, and the manifest permission lists stay byte identical to 1.1.38.

Downloads are consent bounded by the batch grammar: `batchdownload` needs a reviewed `downloadspec` with an HTTPS url list, a filename rule and a completion criterion, the concurrent window is a user configured choice with no code ceiling, filename conflicts resolve with sequence suffixes, and every per file state (queued, running, paused, complete, failed) persists with the resolved path, byte count and checksum. `interceptmime` arms include, exclude and deny default mime filters only while the session origin grants cover the active origin, and the listener never touches downloads the extension itself started. Quarantine is verdict gated twice: a quarantined file stays outside the downloads folder with a pending verdict, and the release action refuses anything but a clean scan verdict while auditing every release with its verdict; the scanning hook is an HTTPS endpoint configured behind its optional origin permission, and hook failures stay pending instead of releasing.

Clipboard reads are consent bounded three times: `readclipboard` needs a reviewed consent ref in the step options, an approved consent prompt in the review panel, and the prompt is single use (every read consumes its own), so no read happens silently. The payload text never persists anywhere — memory, outcomes and logs carry only the length, the deterministic payload hash and a masked length marker, `writeclipboard` writes reviewed text through the page bridge which reports the result with the payload hash, and `copyscreen` copies the visible tab as png data under the optional clipboardWrite capability. Netlog export is bounded the same way: `exportnetlog` is a read only step and every exported record carries its header values redacted.

## Page capture under the active tab grant since 1.1.40

The 1.1.40 media capture family adds no permission: every capture kind runs inside the already granted `activeTab`, `storage` and `scripting` surface, the visible tab capture api needs no optional permission, and the manifest permission lists stay byte identical to 1.1.39. Screen capture beyond the page itself (desktop or tab screencast) stays out of the manifest and out of scope; captures always derive from the page the user granted.

Captures are consent bounded by the capture gate: every capture kind needs the live, unpaused session whose tab matches the active tab and whose origin grants cover the active origin, plus the approved plan, and `shotregion` additionally requires the explicit reviewed flag on every reviewed region rectangle before it runs. Export routing is consent layered: the memory target keeps the bytes in the session store under the user configured capture retention window (expired bytes drop while the metadata survives for the audit trail), the clipboard target negotiates the existing optional `clipboardWrite` capability through the permissions api, and the download target runs only through the reviewed download flow behind the optional `downloads` capability; no other disk route exists. Webp output re-encodes the png shot on the capture canvas because the visible tab api only returns png or jpeg.

## Media capture part two under the same grants since 1.1.41

The 1.1.41 media family adds no permission either: every media kind runs inside the already granted `activeTab`, `storage` and `scripting` surface plus the existing optional `downloads` capability for image batches and pdf downloads, and the manifest permission lists stay byte identical to 1.1.40. Tab screencast, desktop capture and offscreen documents stay outside the manifest by review, so `recordscreen` derives an ordered frame sequence from the visible tab capture api at the reviewed fps and `captureaudio` derives audio element evidence, both stored as honest manifests with a derivation note instead of encoded media bytes; the browser quota of roughly two visible tab captures per second is an external limit and missed frames are counted honestly.

Recordings of user activity are consent bounded three times: `recordscreen` and `captureaudio` need a reviewed consent ref in the step options, an approved recording consent prompt in the review panel persisted per origin, and every start consumes its own prompt, so no recording happens silently. The duration never runs unbounded: it comes from the reviewed step options or the user configured recording window, run scoped recordings stop cleanly at run end and stopping the session stops every active recording. Pdf documents are derived text layer reports composed from page segments because browser print apis stay outside the manifest, and they route only to session memory or the reviewed download flow — never the clipboard.

## Network control without cookies, proxy or net request grants since 1.1.44

The 1.1.44 traffic control family adds no permission either: the required list stays locked to `activeTab`, `storage`, `scripting` and `sidePanel`, the optional list stays `tabs`, `downloads`, `clipboardRead` and `clipboardWrite`, and the forbidden set (cookies, webRequest, declarativeNetRequest, proxy, debugger, history, bookmarks, native messaging, management) stays forbidden in both lists. Request blocking, response mocking and header rewriting steer the extension-initiated traffic of the run: every outbound fetch consults the active rule set first, matched block rules refuse the request with per-rule hit counts, matched mock fixtures serve their reviewed status, headers and body without touching the network, and rewrite rules apply their set, append and remove operations with the provenance of every applied rule audited. Page-initiated requests cannot be blocked without webRequest and stay observable in the 1.1.43 watch buffers instead — the derivation is documented in every step result rather than hidden.

Cookie control runs through the page document cookie jar of the granted origin via the page bridge: writes carry name, value, path and optional expiry, reads return the name and value pairs the origin jar exposes (document.cookie exposes no domain, path or expiry metadata), and clears expire the matched names; every operation is mirrored as a storage-scoped cookie operation record with timestamps while cookie values stay out of the audit trail, and the cookiegate refuses every domain outside the session origin grants so no cross-domain cookie access exists. Proxy routing keeps the proxy permission out: a reviewed route applies for the run only with its bypass list, non-bypassed extension traffic routes through the reviewed relay endpoint pattern (the configured HTTPS endpoint carries the target url in a reviewed header), the route reverts at run end and from a manual revert button, and requests send direct with an audited note when no relay endpoint is configured. The oauth flow opens the provider consent page in a reviewed tab and captures the redirect code through the optional `tabs` capability requested from the review panel — url visibility of the redirect tab is exactly what the code capture reads — while token material stays behind storage ids. Api key storage stays behind the storage seam with the honest boundary that the platform offers no extension key store: key material never enters any report, protocol envelope or audit trail, and entries record last use timestamps instead.

## Debugging part two without the debugger permission since 1.1.46

The 1.1.46 devtools family adds no permission either: the required list stays locked to `activeTab`, `storage`, `scripting` and `sidePanel`, the optional list stays `tabs`, `downloads`, `clipboardRead` and `clipboardWrite`, and the forbidden set (debugger, cookies, webRequest, declarativeNetRequest, proxy, history, bookmarks, native messaging, management) stays forbidden in both lists — the `debugger` permission the chrome devtools protocol needs is exactly what the CLI manifest gate refuses. The reviewed debugger capability of this family is therefore a consent flag, not a manifest permission: the per origin debugger consent prompt shows the domain allowlist (`Runtime`, `Log`, `Debugger`, `DOM`, `Network`, `Page`) before the first attach of a run, the approved decision persists per origin, revocation removes the coverage, and the grant revokes when the run ends, fails or is cancelled. Every command routes through the page-instrumented harness injected by the scripting api — raw commands run as evaluated probes of the `Runtime.evaluate` surface with honest `uninstrumented` error classes for everything else, domain events derive from the harness console hooks and the performance navigation buffer, breakpoints and stepping are reviewed instrumentation hooks of the run's own probes rather than arbitrary page scripts, and script overrides steer instrumented evaluations instead of the network stack. The derivation note rides on every session record, every step result and the changelog; the user detaching the debugger reverts every breakpoint and override, keeps the session record alive for review and pauses the run before continuing.

## Environment emulation without new permissions since 1.1.48

The 1.1.48 emulation family adds no permission either: the required list stays locked to `activeTab`, `storage`, `scripting` and `sidePanel`, the optional list stays `tabs`, `downloads`, `clipboardRead` and `clipboardWrite`, and the `geolocation`, `notifications` and `debugger` permissions the platform masks would need deliberately stay out of both lists — the emulation kinds (`emulatedevice`, `emulatenetwork`, `emulatelocate`, `setuseragent`, `overridepermission`, `blackboxscripts`) all grade sensitive and run behind the consent window beside the scripting grant, exactly like the debugger consent posture above. The emugate is therefore a consent flag, not a manifest permission: a live session on the run tab, an approved plan, the explicit reviewed flag and a reviewed revert plan beside every layer, with the per origin location consent whose prompt shows the exact latitude and longitude before the location layer applies, and the permission layer answering only navigator queries of the reviewed browser permission set while the browser permission itself stays untouched. Every mask is a page-injected derivation of the run tab through the scripting seam (the network layer shapes only extension-initiated traffic, page traffic stays observed only), the derivation note rides on every layer record and the changelog instead of being hidden, and the whole stack reverts in reverse apply order the moment the run ends, fails, is cancelled, navigates away or drops its tab.

## Automation allowlists and originprofiles since 1.1.61

The 1.1.61 security part one release adds no manifest permission: the trust boundary hardens entirely inside the existing `activeTab`, `storage`, `scripting` and `sidePanel` grants with the same optional capabilities. The denydefault posture refuses every origin the user never granted; the per origin automation allowlist persists in the extension storage with one exact origin per entry (no wildcard expansion exists and a wildcard entry refuses the whole check), the active tab grant counts as exactly one explicit single origin grant, and the entries scope per profile workspace. The per site originprofiles persist their action kind grants and denials the policy consults before every sensitive kind, the consentwindows bind every sensitive grant in time with the duration the user chose and a named boundary that never defaults to unlimited, the revokerun halts runs mid step as a terminal session event, the immutable run log chains every entry through its sha-256 loghash with the completion seal and the verified read path, and maskinputs keeps typed, form and stored values behind the documented password, token, card and secret shapes the user extends. See `docs/15.consentmodel.md` for the full consent model.

## Deep manifest check rules (1.1.80)

The `devthink manifest` command verifies every manifest key against the runtime policy allowlist, reports the source file and line of every permission declaration, validates the content security policy script hashes against the bundled script bytes through the digest seam (an unsafe-inline, unsafe-eval or wildcard source refuses and a declared hash that pins no shipped file refuses), validates the web accessible resources against the reviewed resource set (sandbox.html stays the only reviewed web exposed page), refuses a permission that declares in both the required and the optional sets, checks the minimum chrome version against the capability report of the declared apis (sidePanel floors at 114, offscreen at 109, the manifest v3 floor at 88) and validates the icon dimensions and file presence for every declared icon straight from the png ihdr header. A key outside the allowlist is a review miss, never a silent pass; the command exits nonzero when any finding carries the error severity.

## The bridge adds no new host permissions (1.1.82)

The site bridge of the 1.1.82 family adds no new host permissions to the manifest: the relay url is always the user setting typed in the options page, the socket opens through the runtime messaging surface the extension already holds, and the origin checks validate the sender of every incoming extension message while the external connect allowlist restricts which pages may talk to the extension. The bridge sends plan text and statuses only — page content never crosses without the explicit consent flag — and no telemetry leaves the site or the bridge by default.

## The mcp server mode adds no new manifest permissions (1.1.84)

The mcp server mode of the 1.1.84 family adds no new manifest permissions: the stdioserve transport speaks over the process stdio the cli already owns, the httpserve transport binds a localhost port the serve command opens, and the tool calls route through the same policy, kind catalog, memory and progress stores the extension engine already holds. The sensitive tools block until the human approval gate answers and every call lands in the audit trail with the caller, the tool and the outcome.

## The optional native messaging posture (1.1.85)

The native host bridge of the 1.1.85 family declares the `nativeMessaging` permission in the optional set only: the user grants the native transport per install through the host manifest registration, the install consent gate explains the scope before any write, and the deep manifest checks of the cli manifest command refuse the permission in the required set — a required native messaging permission would install a native host grant the user never reviewed. The native transport adds no required manifest permission and no host permission: the transport ships deny by default, nothing native runs until the user installs the companion host, and the per class consent gates, the per surface consents, the kill switch and the escape hatch stay in front of every native call. See docs/17.nativebridge.md for the install walkthrough and the token model.

## Per browser permission overlays (1.1.86)

The 1.1.86 cross browser build keeps one source manifest and per browser overlays. The chromium manifest stays the source of truth; the firefox overlay (`manifest.json` → `browsers.firefox`) layers the `browser_specific_settings` with the generated extension id, the strict min version, the action key mapping, the event page background scripts, the optional permission names that differ, the empty host permissions the deny by default posture keeps, and the web accessible resources firefox pattern syntax. The safari overlay (`manifest.json` → `browsers.safari`) carries the strict min version, the action popup, the empty host permissions, the optional permissions set and the csp overlay. The `offscreen` permission is chromium only — the firefox and the safari overlays drop it and the page falls back to the inline parser. The `sidePanel` permission is chromium only — the firefox and the safari overlays drop it and the polyfill opens a popup window with the same review gate layout. The `nativeMessaging` permission stays in the optional set on chromium only — the firefox and the safari builds drop it and the native transport reports `unsupported` there. The permission deny list (`debugger`, `cookies`, `webRequest`, `history`, `bookmarks`, `proxy`, `management`) stays in force across overlays: a forbidden permission the overlay widens into the required set fails the build before the firefox manifest ships. See docs/18.browsercoverage.md for the apimap table, the per browser permission differences and the signing and notarization path per browser.

## The capability manifest surfaces since 1.1.91

The 1.1.91 api freeze maps every permission the extension requests to its capmanifest surface: the background manifest carries the full permission coverage — the surface that holds each permission, the message types that need it and the action kinds that exercise it — while every other surface carries the slice it consumes, so the extension manifest and the capability manifests never disagree. The apifreeze gate verifies both directions: a manifest permission that maps to no consuming capability refuses, and a coverage entry that names a permission the extension never requests refuses.

| Permission | Requested as | Capmanifest surface | Consuming capabilities |
| --- | --- | --- | --- |
| activeTab | required | popup | The startsession, context and observation messages with the observe and inspect kinds. |
| storage | required | background, mcp | The configure, context, sessions, security and state messages the memory surfaces read and write. |
| scripting | required | background | The execute, preview, map and observation messages with the click, type and highlight kinds. |
| sidePanel | required | sidepanel | The sidepanel surface itself; no message or kind exercises it beyond the panel. |
| tabs | optional | background | The tabsearch, jumptotab, savelayout, windowstate, controltab and settasktabceiling messages with the tablist, querytabs, windowlist and savelayout kinds. |

| clipboardRead | optional | background | The execute message with the readclipboard kind. |
| clipboardWrite | optional | background | The execute message with the writeclipboard and copyscreen kinds. |

| nativeMessaging | optional | background | The native message the native host bridge carries. |
