# Distribution

This document covers every publishing channel of the devthink release, every artifact each channel ships, and the formats an operator consumes: the nuget and maven package contents, the container image usage for self hosting, the vs code vsix installation, and the artifact manifest format. Nothing auto-publishes outside the reviewed release workflow; no channel names a vendor download url, a marketplace endpoint or a cloud default — every registry coordinate below is the destination the release workflow explicitly publishes to, and every configuration value an operator supplies is their own choice.

## The channel map

| Channel | Coordinate | Artifacts |
| --- | --- | --- |
| GitHub Release assets | `wenathlan/devthink` releases of the immutable `vX.Y.Z` tag | every artifact of every channel below, `SHA256SUMS.txt`, `RELEASENOTES.md` and the provenance assets (the sbom, the attestations record and the artifact manifest). |
| npmjs | `@wenathlan/devthink` | `wenathlan-devthink-<v>.tgz` — the library tarball with the fixtures, the declarations, the docs examples and every library bundle. |
| GitHub Packages npm | `@wenathlan/devthink` | the same tarball, published idempotently when the version is absent. |
| GitHub Packages NuGet | `extension` | `extension.<v>.nupkg` — the distribution package described below. |
| GitHub Packages Maven | `io.github.wenathlan:devthink` | the aggregator pom, one module jar per consumption mode, and the extension and declarations classifier zips. |
| GHCR | `ghcr.io/wenathlan/devthink` | the multi stage container image tagged `<v>` beside the `stable` alias (a `pre` suffix for prereleases), with `extension-container.txt`, `extension-container.digest` and `extension-container.json` pinning the exact image. |
| vscode | the release asset `devthink-vscode-<v>.vsix` | the vs code package described below — the operator installs it from the release with their own credentials; the package declares no marketplace url. |
| firefox | the release asset `devthink-firefox-<v>.xpi` | the firefox build ready for the operator's signing path. |
| safari | the release asset `devthink-safari-<v>.zip` | the xcode wrapper skeleton the operator builds from. |
| chromium | the release assets `devthink<v>.zip`, `extension-<v>-source.zip` and `devthink-nativehost-<v>.template.json` | the chromium extension zip, the immutable source snapshot and the native host manifest template. |
| site | the release asset `devthink-site-<v>.zip` | the hashed static site with its immutable cache header configuration. |
| declarations | the release asset `devthink-declarations-<v>.zip` | every declaration file and declaration map for ide integration. |
| provenance | the release assets `devthink-sbom-<v>.json`, `devthink-attestations-<v>.json` and `devthink-artifactmanifest-<v>.json` | the cyclonedx inventory, the attestations record and the artifact manifest. |

The release notes of every release carry the per channel artifact sections that list the artifacts above, so the release body records every artifact per channel and the checksums file covers the assembled set.

## The NuGet package contents

The nupkg of `extension.<version>` carries the chromium extension zip it always carried plus the 1.1.87 distribution set, all under the `contentFiles/any/any` root a package consumer restores:

- `contentFiles/any/any/devthink<version>.zip` — the chromium extension build.
- `contentFiles/any/any/cli.js`, `contentFiles/any/any/headless.js` and `contentFiles/any/any/mcp.js` — the cli, headless and mcp entry bundles of the terminal family.
- `contentFiles/any/any/devthink.umd.js` and `contentFiles/any/any/index.cjs` — the umd and cjs bundles as content assets.
- `contentFiles/any/any/declarations/*.d.ts` — the declaration files for ide integration.
- `contentFiles/any/any/fixtures/` — the recorded page state fixture, the example plans and the mcp client example as sample content.
- the `README.md` at the package root, the `GPL-3.0-only` license expression, the project url and the `netstandard2.0;netstandard2.1` framework targets matching the csproj profile.

The pure `nugetpack` module of the library describes the same layout, the checked-in `extension.csproj` mirrors it and the nugetpack tests assert the mirror never drifts.

## The Maven package contents

The maven distribution carries one module per consumption mode under the `io.github.wenathlan:devthink` aggregator:

- `extension-library` — the jar embedding `dist/index.js`, `dist/index.cjs`, `dist/devthink.umd.js` and `dist/checksums.txt` as resources.
- `extension-cli` — the jar embedding `dist/cli.js`.
- `extension-headless` — the jar embedding `dist/headless.js`.
- `extension-mcp` — the jar embedding `dist/mcp.js`.
- the `extension` classifier zip (the chromium extension build) and the `declarations` classifier zip (the declaration files) attached beside the module jars.

The aggregator pom records the project name, description, url, scm links and the GPL-3.0-only license. The pure `mavenpack` module describes the same layout, the checked-in `pom.xml` and the `mavendist` module poms mirror it, and the mavenpack tests assert the mirror never drifts.

## The container image usage

The image is multi stage: the builder stage runs the whole validation chain (the cli manifest, the cjs require check, the headless smoke over the example fixture, the native smoke and the firefox prep check) before the runtime stage copies only the lean output onto the plain node base. The runtime entry is `node container/run.mjs`, one plain node script with no vendor runtime.

The image exposes three surfaces, each behind environment variables the operator sets:

| Surface | Bind | Port | Path |
| --- | --- | --- | --- |
| the static site | `DEVTHINK_HTTP_BIND` (default `0.0.0.0`) | `DEVTHINK_HTTP_PORT` (default `8080`) | the site root, with `/healthz` answering the health probe |
| the socket relay | the same http listener | the same port | `DEVTHINK_RELAY_PATH` (default `/relay`) |
| the mcp server | `DEVTHINK_MCP_BIND` (default `127.0.0.1` — loopback until the operator widens it) | `DEVTHINK_MCP_PORT` (default `7436`) | `DEVTHINK_MCP_PATH` (default `/mcp`) |

The relay speaks the servercontract: the extension side registers a session with its pairing code, the site side redeems the code, the relay issues one frame token per member (the hash lives in the session records, the raw token only in the memory-only issuance map), routes the events between the two members and sweeps quiet connections inside the `DEVTHINK_RELAY_IDLE_MS` window the operator chose — an absent window never expires a connection. The image tags carry the version beside the `stable` channel alias that tracks the latest release (a `pre` suffix for prereleases), and the digest files pin the exact image hash. The self hosted walkthrough in `docs/examples/selfhosted-container.md` walks the whole flow.

## The vsix installation

The `devthink-vscode-<version>.vsix` release asset is a pure zip-based vsix — no vendor marketplace url and no download url appears anywhere in it. To install:

1. download the vsix from the release of the immutable tag;
2. open vs code and run `Extensions: Install from VSIX...` from the command palette;
3. pick the downloaded file;
4. run `Devthink: open the bridge panel` to open the chatbridge webview;
5. set `devthink.relayurl` to the wss url of the relay you operate — an empty value keeps the webview fully offline and no url is ever assumed.

The webview runs the chatbridge surface with the library esm build the archive carries, keeps the consent gate visible before any socket frame crosses, and asks for the pairing code from the extension options. The package declares telemetry off and no network default; the marketplace metadata check validates these fields before the package ships.

## The artifact manifest format

`devthink-artifactmanifest-<version>.json` lists every artifact of the release:

```json
{
  "name": "devthink artifact manifest",
  "version": "1.1.87",
  "artifacts": [
    {
      "name": "devthink1.1.87.zip",
      "size": 12345,
      "checksum": "64 hex sha256 characters",
      "channels": ["github", "chromium", "nuget", "maven"]
    }
  ]
}
```

The manifest carries no timestamp, so the same artifact set renders byte identical on every run. The build produces the local manifest over the built set (`dist/artifactmanifest.json`), the release workflow emits the release manifest over the published set, and the release verification step (and the verify workflow) assert a set matches the manifest exactly — a missing artifact, a mismatched checksum or an unexpected extra file each fail the check. The checksums file `SHA256SUMS.txt` covers the complete release set with one sha256 line per artifact, and the sbom inventory documents every artifact as a cyclonedx file component with its hash, size and channels.

## Retention, rollback and provenance

Every published release keeps its assets: the GitHub Release assets persist indefinitely and the workflow channel artifacts keep their retention window for re-runs. The rollback procedure pins the previous artifact set through its immutable tag: checkout `v<previous>`, download the release assets of that tag, verify every asset against the pinned checksums of the previous artifact manifest and republish the pinned set on the channels the rollback covers — the pure `rollbackpinnedset` of the artifact manifest module renders the pin. The provenance chain covers the release: the sbom inventory, the sha256 checksums, the provenance attestations created through the workflow identity (no signing key material lives in the repository — the attestations ride the oidc token of the workflow run and any future signing key lives in repository secrets) and the digest files of the container image.
