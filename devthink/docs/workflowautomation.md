# Workflow automation

The workflow phase of 1.1.50 composes reviewed steps into freezable workflows, and 1.1.51 gives those workflows control flow. This document records the workflow grammar, the variable scopes and expressions, the dry run contract with single step debugging, and the control flow grammar of conditionals, branching, loops, parallel branches with joins and try catch with retries and timeouts. The engine lives in the root `workflow.ts` and `controlflow.ts` modules; every page, browser and storage effect flows through the injected executor so the engine stays pure and testable on plain fixtures, and every workflow construct stays inside the consent gates that 1.1.32 established: a live session, an approved plan and origin matching.

## The workflow grammar

A workflow record carries an id, a reviewed name, a positive integer version, the granted HTTPS origins its steps must stay inside, the frozen expanded step list and the reusable block definitions it was flattened from. Composition (`composeworkflow` as the action kind) validates every rule before the record freezes:

- The name is a non-empty string and the version a positive integer.
- At least one granted HTTPS origin exists; composition refuses plain HTTP and ungranted origins, and the proposal parser refuses origins outside the session grants before any review.
- Every step entry is a workflow step or a block invocation; every step carries an id, a lowercase single word kind of the reviewed action vocabulary, a human readable label and optional target, value, JSON options, output bindings, an inline expression and an inline regex rule.
- Blocks carry a unique lowercase name, a label and child steps or further block invocations; block names stay unique and block references must resolve without cycles.
- `expandblocks` flattens every nested block into the executable step list before review so no step stays hidden, and every flattened step carries its innermost block name so runs highlight the active block.
- Bindings reference steps that exist in the expanded list, and `validateworkflow` re-checks before any run that every binding links an earlier step and every expression operand, regex group and interpolation reference a variable some binding, seed input or earlier expression defines.
- The derived risk grade marks a workflow that writes, submits or navigates as sensitive for review; a workflow of interaction steps grades interaction and a read only workflow grades read.

A shareable step template (`savetemplate`) carries a reviewed name and one valid workflow step it shares across workflows. A run (`runworkflow` as the action kind) carries the workflowid of a composed record, the explicit `reviewed: true` run review flag and an optional variables object of string, number or boolean seed values; the proposal parser refuses runs without the run review flag. A dry run (`dryrun`) carries only the workflowid and marks the whole run free of side effects. A delay (`delay`) carries a base in milliseconds and a jitter window, both zero or positive user choices with no code ceiling. An element wait (`waitelement`) carries a non-empty selector, a timeout and a poll interval, all zero or positive user choices. A compute step (`compute`) carries one expression; a variable extraction (`extractvars`) carries a regex rule with its pattern, flags and named capture groups beside the reviewed text. Regex patterns that nest unbounded quantifiers inside quantified groups — the classic backtracking explosion shapes — are refused at proposal time while bounded repetitions stay user choices.

## Variable scopes and expressions

Variables live in typed scopes of string, number, boolean, list and element kinds. The run opens one root scope; every block region opens a child scope that chains to its parent, and resolution walks from the newest scope outward so a child scope shadows a parent name without rewriting it. Bindings link the outcome of an earlier step to a named variable: the dotted path reads out of the step outcome details (an absent path binds the summary) and the raw value coerces into the reviewed kind — a non finite number, a non boolean or a mismatched value refuses the step instead of silently rewriting it. Expressions evaluate between operands that are variable references or literals with the reviewed operator set: add, subtract, multiply, divide and modulo over numbers; equal, notequal, less, greater, lessequal and greaterequal comparisons; and, or and not over booleans; concat and contains over text with contains also answering list membership; and length over text and lists. Operand coercion refuses mismatched kinds — a boolean literal under an arithmetic operator, a string under a logic operator, a list under anything but contains and length — and division by zero refuses the step. `${name}` interpolation substitutes scope variables into step targets, values and options before dispatch, and an undefined reference refuses the step with the variable name. Regex extraction applies the reviewed pattern to the step text and stores the named capture groups as string variables; a group that did not participate lands as an empty string and the no match case is an honest outcome instead of a crash. Every produced and consumed variable name lands in the runlog entry so the panel shows the dataflow, and the variable values per scope persist with the run for inspection after it ends.

## The dry run contract and single step debugging

A dry run evaluates every step of the composed workflow with no page mutation and no storage write. Each step resolves through its read only projection: read class steps report their would be outcome, the delay reports the window it would sleep, the element wait reports the selector it would poll, the compute reports the expression it would evaluate and the extraction reports the captures it would store. Interaction and mutation steps carry no projection, so the dry run refuses them in the runlog with the refusal reason instead of silently skipping them; the refused count travels in the outcome details and the audit trail. Dry run outcomes are marked distinctly from real run outcomes in the timeline, and nothing the dry run touches reaches the page bridge.

Single step execution runs exactly one chosen step outside the run loop: the sidepanel offers it from the step context of a stored run, the step passes the same consent gate, dispatch chain and evidence trail as a run step, its outcome lands in the runlog, and when the chosen step is the next step of the run the checkpoint advances so the run continues exactly there. Runs checkpoint after every completed step, so a service worker or browser restart pauses the run at its last checkpoint and the resume continues from it; pause, resume and cancel record their reasons in the audit trail, and the runlog retention window stays a user choice with no code ceiling.

## Conditionals and branching

A condition step (`condition` as the action kind, graded read because it touches no page) carries one reviewed boolean expression over the extracted values. The step evaluates the expression with the same expression engine every compute step uses, stores the boolean result into the named result variable and reports the outcome with no page side effect; an expression that fails to resolve to a boolean refuses the step.

A branch step (`branch`, also graded read) selects one path by page state and extracted values. The payload carries named paths — each with an optional boolean `when` expression over the variables and the page state — and one mandatory else path, so every branch terminates: the first path whose condition holds wins, a path without a condition matches unconditionally and the else path runs when no condition holds, with an empty else step list being the explicit skip. The page state arrives through the snapshot accessor and exposes `pageurl`, `pagetitle` and `pageready` variables inside the branch evaluation, so a branch can route on the current url, the document title or the load readiness without any extra permission. Path names stay unique lowercase words distinct from the else path name, and the runlog carries the branch decision with the chosen path and the reason it was chosen; the review panel lists every path with the else path previewed, and after a run it highlights the path that ran.

## Loops, safety bounds and foreach

The loop family iterates bodies over data. A loop step (`loop`) iterates a list variable: every iteration deep copies the current item, rebinds the item and index variables and runs the body, so cross iteration mutation cannot leak and the bindings of each pass start clean. A repeat until step (`repeatuntil`) reruns its body until a convergence expression holds. A while step (`whileloop`) loops while its condition holds and refuses to compose without a mandatory safety bound — an endless while loop is refused at composition, and a loop whose condition still holds at the bound reports the overflow honestly instead of looping forever. A foreach step (`foreach`) resolves its selector into element references through the page bridge query seam and iterates them binding an element item with its index; a selector that matches nothing is an honest zero iteration outcome, not a failure.

Safety bounds are user choices with no code ceiling: the loop and repeat until steps accept an optional positive bound and a while loop demands one; an absent bound keeps the documented default of one thousand iterations, any user configured bound wins over it, and the sidepanel lets the user edit the bound of a composed loop before a run (the record recomposes as a new version while the older version survives for the audit trail). Nested loops track an outer and inner index path — `loop[outer].inner[index]` — so the audit counters answer which pass of which loop produced an outcome. Every iteration emits a marker into the runlog, the loop counters land in the control decision of the step, and progress counts the executed iterations over a user defined denominator.

## Parallel branches, joins and merge strategies

A parallel step (`parallel`) runs its branches concurrently: every branch carries a unique lowercase id and a non-empty body, launches inside its own isolated scope chained to the parent, and the sibling variables stay invisible across the branch scopes — a branch that references a sibling variable the sibling has not written fails its own pass rather than reading a half state. The branch count stays a user choice with no engine cap.

The join policy is reviewed with the step. Its `strategy` resolves conflicting variable writes when two branches write the same name: `first` keeps the write of the earliest branch in order, `last` keeps the latest (the default reading of the grammar), and `fail` refuses the whole parallel block with the conflicting names listed. Its `onfail` decides what happens to siblings when a branch fails: `cancel` marks the branches that were still running when the first failure landed as cancelled — cancelled branches never contribute to the join — and fails the block, while `continue` lets the siblings finish and the join merges their writes with the failed branch outcome recorded honestly. The join record with its strategy, conflicting names and merged names lands in the runlog and the audit trail, and the panel renders the branches as concurrent lanes with the join result and the merged variables beneath them.

## Try catch, retries and timeouts

A try step (`trycatch`) wraps fragile steps: the payload carries the fragile body, an error handler with its own child steps and an optional rerun flag, an optional retry policy and an optional timeout policy. When the body fails, the failing error class — the `errorclass` detail the executor reported, or the honest `stepfailed` default — and its message land in the catch decision, the handler steps run through the same step machinery, and the rerun option executes the body once more after the handler; a handler that itself fails fails the block.

The retry policy is entirely user configured: the attempt count carries no code ceiling, the backoff shape is fixed or exponential with a base in milliseconds and a seeded jitter window, and only the reviewed error classes retry — a non retryable failure hands control straight to the catch handler. Exponential backoff doubles the base per failed attempt and the seeded jitter spans half the window around it, so retry windows replay exactly for audits. The timeout policy carries per step and per run millisecond budgets, both positive user values with no ceiling: a step that exceeds its budget is aborted with the `timeout` error class, a whole run that exceeds its budget is cancelled with the cancelled error class carrying the exceeded budget, and the response envelope reports timeout aborts and retry exhaustion distinctly. Every branch, loop, join, retry, timeout and catch decision persists with the run for audit, and the panel renders retry attempts with their backoff countdowns, timeout aborts with the exceeded budget, and try blocks with the catch path that ran after a failure.

## The canvas editor and the block palette

The editor of 1.1.53 lives in the root `workfloweditor.ts` module and stays pure: the sidepanel renders the model and the background validates every save through the same `composeworkflow` grammar every other path uses, so no editor artifact bypasses review. The canvas model (`editormodel`) carries the nodes, the typed binding edges, the block definitions, the layout state, the mini map, the undo and redo stacks and the dirty marker. `loadworkflow` converts a composed record into the canvas: one node per top level step, one invocation node per contiguous block region of the expanded step list — with a unique node id even when one block is invoked many times — and the bindings of every step lifted into typed edges that reference the producing and consuming step ids directly, including steps inside block definitions. `saveworkflow` converts back: step nodes snapped into a block column ride into that block's definition, invocation nodes expand again through the composition, every edge re-binds onto its step, backwards edges refuse so no cycle forms, and the composed record must pass the full grammar before it freezes.

The palette lists curated drop blocks across the five categories of actions, control flow, waits, variables and triggers, and the step library browses every reviewed action kind of the policy table grouped by category with its documented option schema; both filter by search. Drag and drop snaps a node onto the reviewed grid and the nearest block column attaches the step into that block while the main column detaches it. The mini map projects the full canvas into a small rectangle with the viewport inside it, a click jumps the canvas to that region inside the canvas bounds, and the zoom keeps step labels readable at every level by growing the label scale once the zoom shrinks below one. Step search finds steps by label, kind or variable name. Every canvas edit — insertion from the palette, inspector edits, edge wiring and removal, snapping, reorder, grouping into a block, breakpoint toggles, nested param binding — rides the undo stack, and a new edit clears the redo stack.

## Versioning, diffing and templates

Every editor save stores a `workflowversion` record with its number, timestamp, change note, step count and risk grade beside the composed record version, and older versions survive so the timeline renders the whole history. `diffversions` compares two versions into a `versiondiff` of the steps the newer version added, removed and changed with the field names that changed; the panel highlights the three classes and the stored diffs feed the history view. Rolling back composes the stored version as a new record version with a rollback marker on its version record, and the rollback grades unreviewed — the same pending review state as an import — until the user approves the restored step list through the review, so a rollback can never smuggle an old sensitive step list past review. Step templates insert from the shared template library with nested parameters that ride into the block scope, and the debug breakpoints mark any step — top level or inside a block definition — so a debug run executes the segment before the next marked step, pauses there and resumes exactly there through the ordinary run machinery.

## Background runs and the watchdog

A workflow with the background run flag keeps executing in the service worker with no panel open: every step checkpoints the run state, the scopes and the runlog, and every worker wake restores an interrupted run from its last checkpoint through the same session, plan and origin gates — the startup hook marks interrupted runs paused with the interrupt pause kind, and a user or watchdog pause stays paused. The watchdog scans the running runs: a run grades stalled when no step completed inside the user configured stall threshold while its executor lives, and a run grades zombie when its executor is gone — a browser shutdown left it running — and the zombie window elapsed. Stalled runs recover by the user configured retry, pause or cancel action (retry rides the resume machinery through the gates, pause parks the run at its checkpoint, cancel ends it with the reason), and zombies always reap. The stall threshold, the recovery action and the zombie window stay user configured values with no code ceiling, every scan event persists with its recovery outcome, and run history keeps the outcome, duration and trigger cause of every execution under a user configured retention.

## Per site policy overrides

A per site override (`siteoverride`) adjusts the reviewed policy knobs of one workflow for an https origin pattern: the pattern is a bare https origin or a `*` subdomain glob of one, and the deltas may only name the reviewed knobs — `loopbound` for the loop safety bounds, `stepms` and `runms` for the per step and per run timeout budgets, `waitms` for the element wait timeout and `delaybase` for the delay base — each a positive user value with no code ceiling. The override applies to the steps of the workflows whose origins match the pattern: the deltas rewrite the reviewed option payloads of the matching step kinds only, and an override that matches none of the workflow origins refuses. Overrides persist per workflow, render in the editor panel with their knob deltas, and remove on demand.

## Import, export and sharing

A workflow file (`workflowfile` of format version 1) carries the export time, the composed workflow record, an optional change note and the packed step templates of a share bundle, serialized as json or a documented yaml subset of quoted scalars, mappings and block sequences that the reader parses back exactly. The export content review walks every step options object and every packed template payload and refuses the export when any field names a secret, token, api key, password or authorization header — secrets never leave the browser. Importing parses the file, refuses unknown format versions, empty step lists, unreviewed kinds and broken templates, composes the record through the full grammar and grades it unreviewed: the record stays unrunnable until the user approves the expanded step list through the import review, and rejecting the import removes the pending record from the library entirely. Template sharing packs a workflow with its templates into one file so a whole library travels together.

## Trigger rules cross link

Workflows start themselves in 1.1.52: page visits, url patterns, the context menu, keyboard shortcuts, the toolbar button, cron schedules, intervals, url lists, webhooks and observed page events arm as trigger rules that launch reviewed workflows. The whole trigger grammar — the ten rule kinds with their arm reviews, the five field cron expressions with timezones, the interval jitter spread, the webhook secret verification with rotation, the manual run step preview with its confirmation, the keyboard and context menu bindings and the cooldown, dedupe and queue discipline — lives in [docs/triggerguide.md](triggerguide.md). Every trigger launch rides the same run machinery this document describes: the fire becomes a reviewed runworkflow step of its own, the triggering url, title and payload enter the run context as seed variables, and every step still passes the session, plan and origin gates.

## Agent protocol cross link

The composed workflows became server tools in 1.1.54: the browser speaks the open agent protocol over mcp, and any paired client — any llm gateway, agent framework or local process the user pairs — lists the same reviewed vocabulary through `tools/list`, negotiates capabilities and calls `workflow.run`, `workflow.dryrun` or `workflow.triggers` exactly like the panels do. The whole protocol surface — the four tool namespaces with their json schema inputs, the json rpc framing with the error codes, the stdio bridge setup and the capability negotiation with the localhost binding — lives in [docs/agentprotocol.md](agentprotocol.md). Every tool call rides the same gates this document describes: read only tools run under the dryrun risk class once the session is approved, and a workflow launched through the protocol executes exactly the approved runworkflow plan step with its explicit run review — the protocol layer never bypasses review.
