# Agent protocol

The workflow stack has run from engine to editor since 1.1.53, and 1.1.54 turns the browser into a tool server: Devthink exposes its reviewed browser tools over mcp, lists them with json schema inputs, negotiates capabilities with clients, frames messages in json rpc, bridges stdio for local client processes and binds localhost by default. This document records the mcp server and tool list, the json rpc framing and error codes, the stdio bridge setup, and the capability negotiation with the localhost binding. The server lives in the root `mcpserver.ts` module with the tool definitions in the root `toolcatalog.ts` module, and no tool call bypasses the consent gates that 1.1.32 established: a paired client, a live session, an approved plan, origin grants inside the session and, for every tool with side effects, the approved plan step the tool names. No endpoint, provider or key is hardcoded — the server speaks to any client the user pairs, and the bind address, port, transports, frame size and queue depth all stay user configured with no code ceiling.

## The mcp server and the tool list

The tool catalog serves four namespaces and every tool name carries its domain prefix so colliding base names stay unambiguous: `browser.snapshot` and `browser.click` never collide with `workflow.list` or `memory.list`, and a bare name resolves only when exactly one tool of the catalog carries it. Every tooldef appends its own `version` beside the catalog version for compatibility checks — a client that negotiated a tool compatibility floor of version 2 refuses every tool of version 1, and the negotiation never widens what the older tool can parse.

- The `browser` namespace serves the snapshot (`browser.snapshot`), the extraction reads (`browser.extract`, `browser.readtext`, `browser.readtable`, `browser.readlinks`, `browser.a11ytree`), the tab and window inventories (`browser.tablist`, `browser.windowlist`) and the interaction, navigation, tab and window commands (`browser.click`, `browser.type`, `browser.presskey`, `browser.navigate`, `browser.back`, `browser.forward`, `browser.reload`, `browser.tabcreate`, `browser.tabactivate`, `browser.tabclose`, `browser.windowcreate`, `browser.windowclose`, `browser.windowresize`).
- The `workflow` namespace serves the listing (`workflow.list`), the real run (`workflow.run`), the dry run (`workflow.dryrun`) and the trigger listing (`workflow.triggers`) so clients can inspect schedules.
- The `memory` namespace serves the read accessors for stored runs, variable scopes and audit summaries (`memory.list`, `memory.variables`, `memory.audit`) through the new read kind `listruns` and the existing `extractvars` and `trailaudit` kinds.
- The `system` namespace serves the status, version and capability reports (`system.status`, `system.version`, `system.capabilities`).

Every tool maps its inputs to a json schema of typed properties (`string`, `number`, `boolean`, `object`, `array`) with a plain language description, the required list and the reviewed default values; policy validates the whole catalog against the action kind grammar so a drifted tool — an unnamespaced name, a duplicate, a kind outside its domain, an untyped property, a required marker outside the properties or an empty property map — is refused. Tool descriptions state the consent class and the side effects in plain language, and every tool with side effects declares its `consentmeta` review requirement: read only tools take their reviewed `target`, `value` and `options` inputs and run under the dryrun risk class once the session is approved, while every tool with side effects takes only the `stepid` of the approved plan step whose reviewed payload it executes, so a paired client can never widen what the human approved.

## Json rpc framing and error codes

A `jsonrpcframe` carries the `jsonrpc: "2.0"` tag with an `id`, `method` and `params` on requests and the same `id` with either a `result` or an `error` on responses; notifications omit the id and error frames without an id answer `null` so the client can correlate the failure. The wire supports two formats: newline delimited blocks where every line is one compact frame, and http post envelopes that wrap the frame in `{ "transport": "http", "frame": … }` for a posted body. The parse and serialize round trips cover both formats and a malformed line answers with the parse error instead of crashing the intake.

The error codes map onto the classic json rpc numbers with one reserved code: `parse` (-32700), `method` (-32601), `params` (-32602) and `internal` (-32603) keep their classic numbers while `consentrefused` reserves -32001 for every consent gate refusal. The routing table maps five methods to their handlers through `methodentry` records — `initialize` completes the handshake and returns the server info with the protocol version and the plain language consent instructions, `ping` answers keepalive frames with pong, `tools/list` returns every tool with its version, json schema inputs, risk grade and consent metadata, `negotiate` exchanges capability sets, and `tools/call` dispatches one tool behind the consent gates. Frame validation rejects malformed ids, unknown methods, non object params and serialized frames over the user configured frame size; an absent frame size never refuses a frame, the same honesty the queue depth keeps — an absent depth leaves the per client queue unbounded while a configured depth refuses the frame that would exceed it. Request frames serialize per client in arrival order, and the framed logs for local debugging carry only the event, the time and scalar fields so params, results and payloads never leak into logs.

## The stdio bridge

The stdio bridge relays frames between a local client process and the server through the native messaging host manifest: the bridge launches under the host name of the installed manifest (`com.wenathlan.devthink`), stamps the process id the host reports, relays inbound frames from the client wire and outbound frames back to it with per direction counters, and restarts a dead client process on demand with the restart count while keeping its relay counters. The browser itself never exposes the native host process id, so the bridge record carries it only when the host reports it — the launch events persist with their process ids for the audit trail. Under the current permission set the browser refuses the native messaging connection because the manifest keeps its permission list unchanged, so the bridge state stays honestly unavailable in the panel while the frame grammar, the frame intake and the panel path stay fully available; the restart button re-runs the launch attempt on demand. The http transport for remote clients lands in 1.1.55 with its tls, auth and allowlist work.

## Capability negotiation and the localhost binding

Capability negotiation exchanges capability sets: the server offers its protocol version, its identity, the tool compatibility floor (the catalog version), the tool count, the namespaces and the allowed transports, and the client answers with the set it speaks. The negotiation agrees when the protocol versions match, the client requires no tool version above the server floor and no transport outside the server configuration; every mismatch reports its reason in plain language and the negotiated set persists on the client record. The server keeps one `clientrecord` per connected transport with its pairing state — every client starts unpaired and waits for the user pairing approval in the panel, and unpaired, disconnected or dead clients never dispatch tools.

The http listener binds localhost by default (`127.0.0.1` on the documented default port 7436); `localhost` and `::1` count as local while any other bind grades sensitive and needs the explicit remote review before the server accepts it. The server starts only after the user enables it — the protocol surface stays closed by default — and the enablement gate validates the port, the allowed transports of stdio and http, the user configured frame size and queue depth as positive user values with no code ceiling. The sidepanel renders the agent protocol tab with the server status, the start and stop controls, the bind state and port, the connected clients with their transports and negotiated capabilities, the pairing prompt, the disconnect control, the tool catalog grouped by namespace, the bridge status with restart, and the recent tool calls with their caller and outcome; the popup shows the running indicator. Every tool call — with the client id, the namespaced tool name and the origin, never the payload — lands in the audit trail beside the tool call records under the user configured retention.

## The http stream transport since 1.1.55

The 1.1.55 family opens the stream http transport for remote clients. An `httpstreamconfig` carries the posted json rpc endpoint path (`/mcp` by default), the server sent event channel path (`/mcp/stream` by default), the tls termination settings and the user configured heartbeat rhythm — every path, mode, window and ceiling stays a user choice with no code ceiling and no hardcoded endpoint. The transport keeps one `streamchannel` per remote client open for streams, stamps heartbeats on every inbound frame, and closes channels that stay silent past the user configured idle window; the heartbeat report counts the beats, the open and the dead channels. The browser runtime exposes no listening socket under the current permission set, so the frame intake rides the same seam as the stdio bridge — the tls, token, allowlist, scope and approval machinery is fully enforced on every frame while a companion host process can own the socket — and the honest limitation stays documented exactly like the native messaging refusal of the stdio bridge.

The ordered intake pipeline of one remote frame never reorders: tls terminates first (`starttls` refuses the required mode without a valid certificate that matches the user configured sha-256 fingerprint), the session token verifies on every frame (`verifytoken` hashes the presented value through the platform crypto seam and matches the stored `tokenhash`), the client allowlist refuses unknown fingerprints (`checkallowlist`), and the namespace scope check runs before any consent gate so unknown tools fail fast with the params error while ungranted namespaces answer with the consent refusal. Auth failures answer with one fixed json rpc message (`The remote frame failed its authentication handshake.`) that names no client, token or pairing state, and the user configured client ceiling (`enforcemaxclients`) refuses connections past it while an absent value keeps the count unbounded. Policy requires tls for any non localhost transport (`remotetransporttls`), grades the remote transport enablement as a sensitive user choice behind the explicit remote review (`remoteenablementgate`), validates the token lifetimes and approval timeouts as user configured positive values, validates allowlist entries against the known client identities, limits token scopes to the namespaces the user granted and grades the token revocation as an always available user action.

## Pairing, tokens and scopes since 1.1.55

A remote client pairs through the auth handshake: the server issues one `authchallenge` with a single use nonce, the client answers the pairing frames with the nonce and its one time `pairingcode`, and the exchange redeems the code exactly once — a used or expired code never pairs a second client. The exchanged client receives one `sessiontoken`: the raw token leaves exactly once in the exchange answer while the stored record carries only its sha-256 `tokenhash` form, its scopes, its issue time and its user configured expiry; `verifytoken` re-derives the digest on every frame. Token scopes limit which tool namespaces a client may call (the scope check runs before the consent gates), `revokeclient` invalidates every token of one client on demand and stays available to the user at any time, and `expiretokens` enforces the configured lifetime. The client identity (fingerprint and display name) registers with the allowlist entry that carries the granted namespaces and the grant history of every scope change; the memory stores pairing codes with their single use state, session tokens as tokenhash values, allowlist entries with grant history, approval requests and their decisions, auth handshake events with outcomes and client identity fingerprints for allowlist matching, while the audit trail records pair, revoke, expire, allow and refuse events.

## Approval gates, tls and the auth handshake since 1.1.55

Every sensitive tool call a remote client raises lands behind an approval gate: `requireapproval` holds the full call arguments, the reason in plain language and the fields the user marked secret; the sidepanel renders the gate as a card with the client identity, the called tool, the redacted arguments and the approve or refuse controls, while the popup surfaces the pending gates as notifications. `resolveapproval` closes the gate with the acting user and the latency from the raise (the `approvalexec` record), and executes exactly the approved call it holds or refuses it — refused and expired gates never execute anything. An unanswered gate times out through its configurable window and refuses by default (`expireapprovals` marks it expired, `approvaltimeout` documents the refusal disposition). The consent metadata of every tool with side effects now derives its risk class from the policy grading, marks the approval gate requirement and scopes the tool to the session grants (`consentmetagrade` validates the derivation), and the tools/list report carries the full consent metadata of every sensitive tool. The per client tool version floor (`negotiatetoolfloor`) picks the client floor whenever the catalog satisfies it and reports the mismatch otherwise, and the negotiated floor persists on the client record. Tls certificate configuration (the mode and the reviewed sha-256 fingerprint) and the remote endpoint, client ceiling, token lifetime and approval window all live in the agent protocol tab of the sidepanel — the options surface of the extension — with no hardcoded certificate, endpoint or provider.

## Event subscriptions and sampling since 1.1.56

The 1.1.56 family completes the agent protocol with the full client surface. A paired client subscribes to protocol events through the `events/subscribe` frames: the subscription carries its event kinds (`callstarted`, `callresult`, `streamchunk`, `progress`, `resourcedelta`, `sampling`, `cancellation`), an optional origin filter and an optional tool filter, and the server pushes one `events/notify` notification frame per matching event — only active subscriptions whose kinds carry the event, whose origin filter matches when set and whose tool filter matches when set receive anything, and every delivery stamps its last delivery time. Policy grades a subscription read only when its filters exclude the mutation mirror: a subscription that listens to the `callstarted` kind must narrow itself with an origin or tool filter so it never streams the side effect calls of unreviewed origins, and an absent kinds list subscribes exactly the read only observation kinds. `events/unsubscribe` cancels the subscription while the record stays for the audit trail.

Resource subscriptions watch the page state: `resources/watch` starts one watcher with the watched resource name and the page state baseline captured at watch time, every page state read compares the current state against the baseline and the changed keys land as a delta delivery (the baseline absorbs the new state after each push), and `resources/unwatch` cancels the watcher. The browser pushes the page state deltas on every protocol state read — the watched page resource compares the session page state summary (origin, mutation and diff counts) against every active baseline — with the same honesty as the rest of the transport: no listening socket exists under the current permission set, so the deliveries ride the same seam as the frames.

Sampling callbacks ask a client model for a completion: `requestsampling` builds one request that respects the client declared model capabilities (the capability set now carries `sampling`, `prompts` and `streaming` flags — a client that declared no sampling capability never receives one) and strips the page content unless the user granted it, so the prompt that leaves the browser carries page text only behind the explicit grant; the exact prompt payload renders in the panel, the client answer closes the round trip through the `sampling/answer` frames with its provenance times, and policy grades every callback sensitive because the prompt leaves the browser. Prompt tools expose the reviewed prompt library as callable tools: `prompts/list` returns the runreview, pagesummary and failuretriage prompt defs with their declared arguments and templates, `prompts/call` renders the template with the argument substitution (required arguments left empty refuse the render, reviewed defaults fill the rest) and returns the arguments as one tool call the client dispatches behind the same consent gates.

## Streaming, progress and cancellation since 1.1.56

Tool results stream: the call runtime chunks the result content into ordered `streamchunk` records (sequence numbers with a done marker on the final slice) that ride `calls/stream` notification frames, and the panel shows the streaming results as they arrive. Long tools report progress: `notifyprogress` emits one progress notice with its percent, plain language message and cancel hint per boundary, the notices persist for the views, and the popup announces the long tool progress of the in flight calls while the panel stays hidden. Cancellation aborts an in flight call: the `calls/cancel` frames name the call id and its reason, `canceltool` turns the call context cancelled with its end time while the partial result survives for the answer, and the cooperative cancellation seam — a registry the page executors consult before and after every step execution — stops anything further from running; the cancellation propagates to the workflow engine through its own pause machinery, the finished or unknown call ids report why nothing aborted, and every cancellation lands in the audit trail with its preserved partial result named.

## Rate limits and structured errors since 1.1.56

Every client counts its tool calls inside a per client rate limit: the window resets past its end, a configured budget refuses exactly the call that would exceed it and the refusal answers with a structured error carrying its retry after window, while an absent limit or an absent budget keeps the client unbounded because no silent default ever applies — the same honesty as the queue depth and the frame size. Policy validates every window and budget as a positive user value. Structured errors map executor failures onto codes with retry hints: timeouts stay retryable, busy windows and rate limits wait for their retry after, and consent refusals never retry; the structured error report carries the code, the message, the hint, the retry after and the usage that produced it, so a client can always correlate the failure with its next reviewed step.

## Idempotency, batching, dry runs and tool mocks since 1.1.56

Idempotency keys replay stored results: a tools/call frame may carry one key, the first call stores its result under the key with the user configured window, and a repeated call of the same client replays the stored result instead of executing — marked as a replay in the answer, the call log and the audit — while a key of another client never replays across clients and an expired record never replays after its window (the maintenance sweep expires the records with its audit). Batch calls run ordered members: `calls/batch` carries the ordered tool calls and the stop on error flag, every member runs through the same call runtime behind the same consent gates, each member lands its own outcome, a batch grades by its most sensitive member (a sensitive batch runs only when every sensitive member names its approved plan step) and the batch stops at the first error when the flag requests it — the per item outcomes persist for the panel's batch progress view. Tool dry runs evaluate without side effects: a `dryrun` flag on the call or the armed panel toggle routes the call through `dryruntool`, which validates the arguments against the tool json schema, evaluates the same consent gates and returns the findings while the record stays executed false with an empty mutation list — the purity gate refuses any dry run record that claims otherwise. Tool mocks answer declared tools with canned results in test contexts only: a mock never touches the browser, the audit records the mocked answer, policy refuses any mock outside a test context, and the panel registers and removes mocks for client testing. Every tool call — live, replayed, dry run, mocked or batched — lands its audit entry with its call id, idempotency key and outcome without exception; the audited call log returns under client, tool, outcome, time and limit filters, and the call contexts isolate the concurrent calls of concurrent clients on one tab session through the same per client serialization the frames already keep.

## Model drafted plans since 1.1.57

The llm integration drives the same protocol surface with model drafted plans, and the review flow is the plan review flow: the routed model returns a plandraft with steps and open questions, the plan lint checks every drafted step against the action grammar before review, the `modelproposal` envelope carries the draft to the human review with its lint findings and model provenance, and the review card edits and approves or rejects it. An approved draft converts its steps into a **pending** plan that still passes the same `approve` review every local plan passes — a draft with grammar findings or unsupported kinds refuses, so nothing a model drafts ever reaches the page bridge before the draft review and the plan review both approve. A failed run replans through the model: the completed steps stay, the failed ones drop and the revised tail steps carry the fresh review marker; the replan review highlights the changed tail and its approval builds a new pending plan behind the plan review again.

## Intents and command parsing since 1.1.57

Natural language commands enter through the panel command box and answer as `commandparse` results: the intent (one of navigate, extract, fill, monitor, automate and ask), the extracted entities of `{ name, value }` pairs and the confidence between zero and one. The parse rides the routed model of the `parsecommand` task kind; when no route serves it the local model endpoint answers, and when neither exists the deterministic classifier maps the request from keyword density alone so the panel always answers. The `modeloutcome` envelope reports the usage totals of the model calls with every guard verdict and its reason. See `docs/llmguide.md` for the full user guide.

The 1.1.58 swarm rides the same protocol grammar: the `swarmstatereport` envelope carries every agent, the shared task queue and every mailbox beside the killswitch state, and the `agents/notify` notification frames push the agent lifecycle events; the task queue, mailbox and blackboard grammar is documented beside those envelopes in `protocol.ts` and in `docs/multiagent.md`.
