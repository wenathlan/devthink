# Security model

Devthink 1.1.62 finishes the security core started in 1.1.61 by protecting secrets, messages and money. The consent gates do not move: every security operation rides the same session, plan and origin review, no security record ever bypasses the human review, and no threshold, bound, window or sender list is ever hardcoded — they are user choices.

## The secretvault

Secrets live behind a vault seam: values enter through `put` and leave through `fetch` at the last possible moment before a credential field, while the persisted records carry only the label, the exact origin scope, the profile workspace, the provenance and the sha-256 verification digest. No plaintext value ever reaches a storage writer, a log entry, a memory record or an export path. `secretleakscan` refuses plan texts, variables and step options whose value digests to a stored vault record, and `secretshapecarrying` refuses a raw typed value behind a masked field shape — a credential step names its vault label and the executor resolves `vault:id` markers through the seam at dispatch time, so the value flows from the vault to the field with no logging. Honest limit: the browser offers no vault hardware, so the background wires the seam to the session storage area (memory only, never persisted to disk) with an in-memory fallback; the persistence layer stores metadata alone, mirroring the immutablelog seam honesty.

## redactshots

Sensitive capture regions never reach the stored bytes. Regions carry their geometry in css pixels, a plain language reason and a source — derived from the masked field shapes of the form layout (`fieldshaperegions`) or drawn by the user — and they scope to one origin and one page template. The capture executor draws the opaque overlays inside the page before every shot of a capture step and removes them after, so viewport, element and stitched captures alike store masked bytes, and the stored record carries `redacted` with the region count as redaction evidence. The transparencypage manages the regions with a drawing form; no region count or geometry is capped by the engine.

## schemastrict, origincheck and connectallow

Every inbound command validates under schemastrict before dispatch: each command names its kind, and every family the registry covers (the security, environments, transparency, execute and configure families first) rejects unknown fields and shape mismatches with the path and the expected shape, echoing no payload — the registry documents the staged rollout honestly and grows with the surfaces. Every runtime message passes `origincheckof`: an internal sender of this extension accepts, an external sender accepts only when its sender id sits in the connectallow list, and every other sender drops without handler execution. Every port connection passes the same grammar through `portaccept` and closes at the handshake when the sender sits outside the list. The connectallow list ships empty by default and holds user managed entries only.

## ratelimit buckets

Automation commands bound per origin and per session under user configured buckets: `bucketconsume` consumes a slot inside the bound, defers a command past its bound until the window resets, and starts a fresh window after the reset. A deferred command records a deferred event with its reset time, appends a suspension entry to the immutable log and lands its audit entry; the sidepanel shows deferred steps with their bucket reset time. No bound or window carries a hidden ceiling — an origin without a bucket runs every command because the bounds stay user choices only.

## confirmpay, confirmdelete and confirmcreds

Payment class steps pause in front of confirmpay, destructive delete steps pause in front of confirmdelete and credential use steps pause in front of confirmcreds. Each gate shows exactly what the human reviews — confirmpay shows the amount, the payee origin and the target element; confirmdelete shows the target, the scope and the irreversibility; confirmcreds shows the credential label only, never its value — and each gate resolves only through one distinct human action: no timeout ever resolves a gate, no batch approval resolves two, and a refused gate never dispatches its step. Gate opens, resolutions and phishguard denies land in the immutable log, the resolutions persist with their human action provenance, and the progress log records the gate wait beside the step durations.

## phishguard and safedefaults

Before a credential step runs on a new origin, the phishguard compares the login target against every granted origin and measures the lookalike distance over the registrable ordered host labels. A distance that crosses the user threshold (a value between zero and one the user chooses, never an engine default) blocks the step and the deny event names the matched known origin; verdicts persist with their distance scores and expire past the user configured freshness window while the records survive for the audit trail. Origins without an originprofile receive the safedefaults posture: the documented read kinds grant on the first visit while every sensitive class denies, the first seen origin records for the audit trail, and the popup notice links to the originprofile editor because only the user widens a safedefaults profile.

## Untrusted markup and the permdiff transparency

Extracted markup grades untrusted before any render: `untrustedrendergate` routes every untrusted render through the 1.1.60 sandboxframe under its nonce and refuses injection into the page context. Each installed update records its permdiff — the added and removed permissions between the stored set of the last version and the current manifest — and the transparencypage lists every active grant with its origin, scope and boundary beside a revoke action, every consent window ever granted with its expiry, the connectallow senders, the permdiff of each installed update, the safedefaults applications and the secretvault labels (never values), served by one memory read through the versioned transparencyreport envelope.

## Bridge threat model (1.1.82)

The site bridge widens the trust boundary to one user configured relay, so the threat model names each exposure and its control. An unpaired sender cannot talk to the extension: the origin checks validate the sender of every incoming extension message and the external connect allowlist restricts which pages may talk to it. A stolen pairing code cannot pair twice: the code redeems exactly once and expires inside its window. A replayed frame cannot impersonate a member: every frame authenticates with the session token, the sha-256 digest must match an unrevoked record of the session, and the token rotates on every reconnect so an old token dies with the socket it rode. A flooding sender cannot drown the bridge: the rate limiting caps the bridge messages per session per second and the audit trail records every bridge event with its session id and operation. A curious relay cannot read the page: the data minimization sends plan text and statuses only, the page content keys refuse loudly without the explicit consent flag, and the relay sees metadata only — never page content. A leaked token cannot live forever: the relay sessions expire after the configurable idle window, the tokens never appear in urls or logs, the one click revocation stamps every record, and the kill switch disables the socket and the pairing instantly. The site and the bridge collect no telemetry by default, and the extension ships no hardcoded relay url or vendor endpoint anywhere — the scan test enforces it.

## Gateway key handling (1.1.83)

The provider keys live in the keyvault and never anywhere else: the storeproviderkey seam writes the key behind its storage id with the consent stamp, the resolveproviderkey seam resolves the material at the last possible moment before the request leaves, the revokeproviderkey seam drops it on demand, and the keyexportcheck refuses any export that carries a key shape. The requests mask before any log (the authorization header and the key query parameter of the gemini shape mask to their label), the gateway error surface carries no key material, and the api key literal scan of the built bundles enforces that no key shape ever ships inside the dist artifacts. The hardcoded provider url scan of the shipped sources enforces the same posture for the endpoints: no api.openai.com, no api.anthropic.com, no generativelanguage.googleapis.com and no cloud ollama url exists anywhere in the shipped code — the endpoints are always the user's configuration.

## Remote caller threat model (1.1.84)

The mcp server mode widens the caller boundary to remote clients, so the threat model names each exposure and its control. An unknown client cannot connect: the client allowlist restricts which clients may pair and the auth handshake requires the token exchange of the servercontract pairing family for any non localhost connection. A flooding client cannot drown the server: the rate limiting caps the requests per client. A confused deputy cannot execute sensitive tools: every sensitive tool blocks until the human approval gate answers (the gate renders in the sidepanel with the caller and its intent), the consent requirements refuse execution when the grant is missing, and the server degrades to read only tools when no origin grant exists. A replayed call cannot double apply: the idempotency keys deduplicate the repeated calls. A curious client cannot read the unreviewed state: the resourceexpose surfaces publish exactly the page state, the plan, the audit trail and the session record, the tool results return the same structured details as the sidepanel steps, and every tool call writes its audit entry with the caller, the tool and the outcome. A lost client cannot hold a session: the session tokens pair a client with one extension session, the bindings release when the client disconnects, and the shutdown drains the in flight calls before the exit.
