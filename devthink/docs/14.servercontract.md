# Servercontract of the site bridge

The servercontract is the wire protocol the static devthink.pro site and the extension speak through one user configured relay. No platform functions are involved anywhere: the relay is a plain websocket endpoint the operator chooses, the site is a static bundle, and the extension stays the only executor. This document specifies every envelope, every operation and the relay expectations of any static host plus open socket deployment.

## The envelope

Every frame is one json envelope. The `version` field carries the servercontract version both sides negotiated (the current version is 1), the `op` field carries exactly one wire operation, the `opid` field carries the stable operation id one reply correlates (`op-<sender seed>-<sequence>`, unique inside one session without any randomness on the wire), the `sessionid` field carries the session the frame belongs to once it exists, the `token` field authenticates the frame with the sharedauth session token, the `at` field carries the epoch millisecond and the `body` field carries the operation payload. An envelope that fails the schema validation refuses with the path that names it.

```json
{ "version": 1, "op": "eventpost", "opid": "op-site-reviewer-4", "sessionid": "session-78dd8c73", "token": "raw-session-token", "at": 1788124800000, "body": { "kind": "chat", "stream": "chat", "payload": { "text": "collect the pricing table", "from": "site reviewer" } } }
```

## The operations

| Operation | Direction | Body | Reply |
| --- | --- | --- | --- |
| `sessioncreate` | extension → relay | `{ role: "extension", memberid, capabilities, pairingcode? }` | `{ sessionid, token, capabilities, members }` |
| `sessionjoin` | site or extension → relay | site first join: `{ role: "site", memberid, capabilities, pairingcode }` · reconnect: `{ sessionid, role, memberid, capabilities }` | `{ sessionid, token, capabilities, rotated? }` |
| `eventpost` | member → relay | `{ kind, stream, payload }` | routed to the other member |
| `eventstream` | member → relay | `{ streams, since? }` | `{ streams, subscribed: true }` |

The sessioncreate operation serves the extension member only: the extension creates the session, registers its pairing code and receives the first token. The site joins through sessionjoin with the pairing code — the pairing code matches no pending session, an already used code or an expired code refuses. Every reconnect joins the existing session and rotates the token: the reply carries a fresh token and the old one revokes.

## The event types

| Event | Stream | Payload |
| --- | --- | --- |
| `chat` | chat | `{ text, from }` — the task text and its sender, trimmed and non-empty |
| `planproposal` | review | `{ proposalid, title, steps: [{ id, kind, origin, sensitive }], at }` — the review card |
| `planreview` | review | `{ proposalid, decision, by, note?, at }` — the decision that returns to the extension review gate |
| `progress` | progress | `{ stepid, status }` — the step statuses of the run |

The chatbridge widget on the site renders the conversation and the review cards; it never executes actions — the extension stays the only executor, and the sensitive steps approve only through the extension approval flow. The data minimization holds on the wire: the bridge sends plan text and statuses only, page content never crosses without the explicit page consent flag, and the held keys refuse loudly.

## Capability negotiation

The handshake carries the `capabilities` of both sides: `{ version, operations, events, heartbeat, multiplex }`. The negotiated version is the newest both sides speak, the operations and event types are the intersection in the stable contract order, and a handshake with no shared version, no shared operation or no shared event type refuses instead of degrading silently. The heartbeat flag and the multiplex flag both sides must declare.

## Relay expectations

Any static host plus open socket deployment serves the relay role when it holds these expectations: it accepts one extension member and one site member per session, it routes the eventpost frames between the two members of the session, it authenticates every frame with the session token (the sha-256 digest of the raw token must match an unrevoked record of the session), it rotates the token on every sessionjoin reply, it expires the sessions after the idle window the extension configured, it never logs a session token, and it sees metadata only — never page content. The relay url is always a user setting (wss scheme, validated for scheme, host and port shape before saving; empty disables the bridge completely), the extension ships no hardcoded relay url or vendor endpoint anywhere, and the site asks the visitor for the relay url before connecting and stores it in the browser localstorage.

## Pairing walkthrough

1. The operator opens the extension options and types the relay url (wss, always the operator's choice; an empty value disables the bridge).
2. The operator consents to the first socket connection — the bridge consent gate asks before any socket opens.
3. The operator mints the pairing code inside the extension options; the code shows with its expiry countdown (the documented five minutes unless the operator configured another lifetime).
4. The visitor opens the static site, types the same relay url and the pairing code, and pairs: the site sessionjoins the extension session through the code.
5. The conversation flows — the site sends the task text, the extension proposes plans as review cards, the site returns the review decisions to the extension review gate, and the extension alone executes what the review approved.
6. The operator revokes all sessions with one click whenever the pairing should end; the kill switch disables the socket and the pairing instantly.

## The mcp event envelopes (1.1.84)

The mcp server mode reuses these servercontract envelopes for its event streams: the server events that carry the plan progress to the subscribed clients ride the same envelope grammar, the session tokens pair a client with one extension session through the same sharedauth exchange, and the remote caller auth handshake of the httpserve transport uses the same pairing code mint and redemption. A client that speaks the servercontract and a site that pairs through the chatbridge authenticate against the same session machinery.

## The native frame envelopes (1.1.85)

The native host bridge reuses these servercontract envelopes for its wsbridge frames: every native frame rides one `eventpost` envelope with the negotiated contract version, the stable operation id, the multiplexed stream name `nativetransport` and the native frame as the stream payload — the frame carries its kind (handshake, call, event, heartbeat, advertisement or error), its correlation id of the run, its session id for the origin and session checks and its body. The wsbridge authenticates every incoming envelope against the per session token before any body read, holds exactly one extension connection at a time and expires a quiet session after the user configured idle window; the advertisement that carries the port and the raw token rides the native port only, while every stored session record keeps the sha-256 hash. See docs/17.nativebridge.md for the token model.
