# DevThink 1.1.12 design references

## Welcome and connection frame

The first supplied frame uses one centered dark connection card over a soft, desaturated blue atmospheric background. Its hierarchy is narrow and deliberate: one mark, one concise welcome statement, one line of explanatory copy and a short vertical action stack. The DevThink interpretation retains a single canonical ANSI mark and a connection choice surface, but only offers explicit local pairing, user-provided official provider keys or provider-owned official OAuth flows.

## Settings frame

The second supplied frame uses a restrained charcoal settings rail divided into clear semantic groups. A single active row receives a quiet rounded material treatment, while lower-priority options remain plain. The DevThink interpretation will use the same grouping principle for local workspace settings, provider controls and pairing status, but it will not duplicate the third-party branding, labels or navigation structure.

## Shared principles identified so far

The common direction is dark charcoal rather than pure black for utility frames, soft blue environmental depth for connection states, one focal card or frame per screen, grouped navigation, unobtrusive icons and one strong primary action. The DevThink signature remains its own: black workspace base, orange intentional action, orb-blue local state and the canonical ANSI identity.

## Catalog and control frames

The third reference shows a wide catalog page: a stable left settings rail, a single concise title, a search field, compact category controls and content rows with sparse metadata. The fourth reference uses the same shell for a safety-sensitive configuration page: two grouped charcoal cards, one binary control and one clearly destructive operation. DevThink should adopt the density discipline, labeled groups, modest card radii and clear destructive-action separation. It must not reproduce browser-cookie controls or third-party automation concepts; its equivalent settings are local gateway, provider readiness, theme, pairing and explicitly user-owned data removal.

## Provider configuration frame

The fifth and sixth references show the same provider editor: a narrow provider list beside a form with explicit endpoint, protocol and model fields. The useful shared principle is not the exact control styling; it is the visible distinction between provider selection and provider mutation. DevThink will expose the same model of a selected provider, base URL, official credential method and model list from web and CLI. The paired web client sends the mutation to the local gateway, which writes it to the CLI-owned configuration and database; the browser never persists raw provider keys.

## Provider state frame

The seventh reference adds visible readiness and capacity state to the selected provider; this is useful when represented as plain local status, configured models and usage summaries. The eighth reference reiterates the provider editor. The DevThink equivalent will show only locally verifiable configuration and usage data returned by the user-owned gateway, never fabricated quota data or credentials. Provider state remains a tab section and may be opened as its own session tab.

## Workspace and handoff frames

The ninth reference centers a single composer beneath a concise greeting and a few practical suggestion cards. It confirms that the main work surface should remain quiet until the user supplies intent. The tenth reference depicts an external application handoff after an OAuth-like flow. DevThink may present a generic official-provider completion frame only after a user-initiated, documented flow; supplied redirect addresses, one-time codes, state values and app-open prompts are not copied, stored or used. The safe DevThink equivalent is a local pairing confirmation backed by a short-lived token issued by its own gateway.

## Authentication boundary

The eleventh reference reiterates a handoff prompt, while the twelfth contains a third-party credential screen with a human-verification control. Neither is a DevThink implementation target. DevThink does not collect third-party passwords or verification challenges in its own UI. Its first-party browser frame is limited to a locally generated pairing identifier and short-lived confirmation code; official provider authentication is delegated to the provider’s documented flow and only the resulting user-authorized credential is accepted by the CLI when supported.

## Onboarding framing

The thirteenth and fourteenth references repeat a compact centered onboarding card with large surrounding whitespace. The transferable lesson is to keep a welcome frame singular and calm. DevThink will use this scale only for its own local pairing and first-intention states, rendered in the product’s black, orange and orb-blue palette. It will not reproduce external login fields, social-login affordances or human-verification controls.

## Final synthesis

The fifteenth reference repeats the dark connection-card composition. The final reference demonstrates a sparse full-height application shell with a persistent side control area, a single central empty state and a bottom utility strip. Taken together, the references favor one product identity per frame, a quiet canvas, compact controls and explicit modality changes. DevThink will render the same principles as a tab-first workspace: session and section tabs are primary; a rail is a user-selectable layout mode for wide screens; the bottom composer stays stable. The design remains original in brand, palette, content and interaction.
