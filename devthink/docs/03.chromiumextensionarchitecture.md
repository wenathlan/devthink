# Chromium Extension Architecture Evidence

The extension design will use Manifest V3. Its background context is event-driven, not a permanent background page, so an extension alone cannot guarantee an autonomous process that remains active twenty-four hours per day. Long-lived work must be delegated to a separately operated service or a user-controlled local host; the extension acts as the consented browser bridge. [1]

| Platform capability | Verified constraint or behavior | Devthink design decision |
| --- | --- | --- |
| Manifest V3 | Executable JavaScript must be inside the reviewed extension package; remote code is prohibited. | Remote endpoints may deliver declarative, schema-checked task data, never executable extension code. |
| Permissions | Optional API and host permissions can be granted by the user at runtime. | Start with `storage`, `activeTab` and `sidePanel`; request a target origin only after an explicit session request. |
| Side Panel | Chrome 114+ MV3 supports an extension UI alongside a web page and can limit panel availability to a specific site or tab. | Provide a task review and session-control companion surface rather than hidden page automation. |
| Internal messages | Chrome uses JSON-serializable messages. Content-script messages must be treated as untrusted input. | Validate every message envelope, bind it to tab/origin/session and keep privileged decisions in the service worker. |
| External messages | A webpage must be allowlisted in `externally_connectable` before it can address an extension. | Do not expose a public web-page command API in version 1.1.1. A future bridge must require explicit, configurable allowlists. |

Chrome documents that host permissions enable access to sensitive tab data and programmatic content-script injection. It recommends optional permissions wherever functionally possible because they give users more informed control. [2] The message-passing guide also warns that content scripts are less trustworthy and that their input requires validation and sanitization. [3]

## Firefox WebExtensions Compatibility

Firefox documents the same minimal-privilege direction: an `activeTab` grant is limited to the tab present at a user action and ends when that tab navigates. Runtime host permissions are expressed through `optional_host_permissions` in Manifest V3. [5] Internal messages are asynchronous and promise-based; cross-extension communication can be restricted with `externally_connectable`. [6]

Native messaging is not a browser-control shortcut. It needs a separately installed native host, an explicit `nativeMessaging` grant, and an allowlist in the native-host manifest. The extension cannot silently install or manage that program. [7] Devthink will therefore ship the browser-only core first and retain any native bridge as a separately reviewed, opt-in target.

## Performance architecture (1.1.68)

The performance part one release keeps the startup path light and the hot paths cached. `lazymods` declare the heavy parsers (htmlsnapshot, readertree, tablerows, a11ytree, diffpreview) and the capture, compare and export families as lazy modules that resolve on first use behind their commands; every module declares its capability requirements ahead of load and the loader runs exactly the capability checks the eager path runs, so lazy loading stays transparent to the review. The prewarm hook warms the user chosen set on startup while the user configured startup module budget reports overruns without ever refusing a load — no engine ceiling exists. The dom observer debounces rapid mutation bursts into one batch, `debouncedom` coalesces scroll, input and resize storms per user configured window, and the snapshot builder folds repeated selectors into one `batchquery` pass that executes as one offscreen worker task. `incrsnapshot` computes deltas against the base snapshot ref of the same run with stable region fingerprints, emits only changed regions, returns a full snapshot on the user configured cadence, and the observation schema carries its delta flag; `selcache` caches selector resolutions per generation and refuses stale hits with a reviewed retry hint. `virtlist` renders the long surfaces through a virtualized window with measured height maps. `streamparse` tokenizes oversized pages chunk by chunk inside the worker pool without ever holding the full page text and `chunkextract` slices big tables into resumable row windows that carry their table fingerprint. The worker queue gains backpressure that defers parse tasks past the user configured depth instead of refusing them, and every step records a perf record (duration, query counts, cache hits, provenance) beside its outcome. The manifest permissions, the pinned identity key and the 334 action kinds stay untouched: performance work never bypasses a review and never adds a permission.

## Scheduling architecture (1.1.69)

The performance part two release makes the platform from 1.1.68 polite, measured and budgeted. The batch run queue pauses its enqueueing when the completed outcomes fall behind past the user configured backpressure window while every queued step stays queued, and every domain runs at most its user chosen concurrency slots with the overflow queued per domain lane that the sidepanel renders during batch runs. Batch requests space themselves through the politedelay profile with its jitter window and its per domain floors, the adaptivepoll window widens while observations stay unchanged and narrows the moment changes resume, identical pending queries merge into one dispatch whose single result fans out to every waiter, and the snapshot cadence widens under memory pressure and restores when the pressure clears. Every run tracks a runbudget record — the step usage against the user step budget and the memory pressure the worker telemetry reported — and the budgetalerts fire at the user thresholds: the warning level reports while the critical level pauses the run pending a user choice through the session pause. The timeoutcancel races the reviewed dispatch against the user chosen bound and records its cancel event in the immutable log beside the step outcome; the tabsuspend suspends an idle tab only during a wait longer than the user window and restores it before the step that needs it with the run state preserved. The runcache stores fetched resources per run keyed by their digest and clears at the run end unless the user pins the profile cache, the stepprefetch derives its warming hints from the plan structure alone behind a gate that refuses anything outside the reviewed plan, the efficientresume checkpoints every step boundary with its cursor and page digest, the navdedupe skips navigations to the already active url, and the sessionreuse attaches an authenticated profile only through its explicit per profile consent prompt with the cookies isolated per task. The durationmeter writes monotonic step samples into the perf records, the selectorprofile flags the selectors above the user latency threshold, the steptrace spans nest per step and per worker task and export as one trace file, the startupmeter measures the cold start against the user target, the artifactcompress keeps the stored bytes deflated at rest with lazy reads, the logprune removes whole sealed runs past the user windows only, the batteryaware scheduler defers non urgent scheduled runs on a low battery and the networkaware retries honor the server signals. The manifest permissions, the pinned identity key and the 334 action kinds stay untouched: scheduling optimizes the pacing of reviewed steps and never bypasses a review.
