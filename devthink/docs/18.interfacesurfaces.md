# Interface surfaces

The 1.1.64 family gives the interface its first five full surfaces. This document describes the five surfaces and their routing, lists every commandpalette command and scripts the onboarding walkthrough. The consent gates do not move: every surface action rides the same session, plan and origin review, the command bus records each routing in the audit trail, and no interface surface ever bypasses the human review.

## The five surfaces and their routing

| Surface | Role | Entry |
| --- | --- | --- |
| popup | The command surface: the taskinput, the quick run actions, the commandpalette with its keyboard shortcut, the origin allowlist state, the environment status and the onboarding walkthrough card | The toolbar button |
| sidepanel | The workspace: the plan, run and review tabs, with the taskinput box at the top of the plan tab, the plancards, the stepstimeline and the live logstream in the review tab | The toolbar review button, `chrome.sidePanel.open` |
| dashboardpage | The full page view in a new tab: the sessiongrid and historysearch of 1.1.63, the site notes, the transparency views and the onboarding state | `chrome.tabs.create` from the popup and the sidepanel, and the new tab chrome url override |
| optionspage | Every setting in one page with sections: the onboarding replay, the palette recent window and shortcut, the logstream live buffer bound, the taskinput history retention, the diffpreview offscreen offload ceiling, the session interface options and the embedded transparency, consent and security sections | The options entry of the manifest and `chrome.tabs.create` |
| onboarding | The first run walkthrough: origin grants, plan review, run control and log audit, run once on install and replayed on demand | `chrome.runtime.onInstalled` with reason install, replayed from the optionspage |

Routing is uniform. Every surface action travels as one `surface` command through the command bus: the bus resolves the command against the palette catalog, checks it through `paletteactiongate` (the existing permission gate of the action), `taskinputproposalgate` (the same proposal flow as the api) and `planreviewgate` (the plancard review before any execution), records the routing in the audit trail under the `surface` kind and dispatches the session commands through the same handlers the popup and the sidepanel always used. The `stepapprove` and `diffpreview` commands additionally ride `stepapprovegate` (one step per distinct human action, no batch, no background provenance) and `diffpreviewgate` (write class steps only).

Live updates travel on one broadcast channel named `devthinksurfaces`. The background posts one frame per audited event through `broadcastchannelof`: run control kinds carry run state, session store kinds carry session updates, configure kinds carry settings changes and everything else streams as logstream frames. The popup refreshes its live status from each frame, the sidepanel subscribes its logstream view, the dashboardpage follows session and run updates and the optionspage reloads its inputs on settings frames. The logstream itself keeps the full event history in memory while the bounded live window follows the user configured `logstreambuffer` bound with no engine cap; every event carries the mask verdict of its source payload and chains through a sha-256 hash the surface verifies live as entries arrive.

## Every commandpalette command

The palette registers its catalog from every module at startup through `surfacepalette()`, lists only the actions the current capability set and session state allow, fuzzy searches ids, labels and keywords and ranks the recent commands first through the stored usage counts.

| Command | Label | Needs session | Opens on |
| --- | --- | --- | --- |
| starttask | Start task | starts one when none is active | popup |
| pauserun | Pause run | yes | popup |
| resumerun | Resume run | yes | popup |
| cancelrun | Cancel run | yes | popup |
| resumesession | Resume session | no | sidepanel |
| stepapprove | Review step | yes | sidepanel |
| diffpreview | Preview step diff | yes | sidepanel |
| historysearch | Search history | no | dashboardpage |
| revokeconsent | Revoke consent | yes | dashboardpage |
| opentransparencypage | Open transparency page | no | optionspage |
| opendashboardpage | Open dashboard | no | dashboardpage |
| openoptionspage | Open options | no | optionspage |
| copyauditexcerpt | Copy audit excerpt | no | dashboardpage |
| replayonboarding | Replay onboarding | no | onboarding |

The palette opens from a keyboard shortcut in every surface: the documented default binding is ctrl+period and the `paletteshortcut` setting overrides it; the `paletterecents` setting bounds the recent window the ranking lifts first.

## The onboarding walkthrough script

The walkthrough runs once on first install (`chrome.runtime.onInstalled` with reason `install`) and replays on demand from the optionspage; a full completion writes exactly one consent scoped event into the consent memory and never a second one.

1. **Origin grants** (popup): Devthink denies automation by default; grant one exact origin at a time from the popup and every run stays inside the granted origins. Completion event: `origingrantscompleted`.
2. **Plan review** (sidepanel): every task becomes a plan of reviewed steps; read the plancards of each risk class and approve, reject or edit one step at a time. Completion event: `planreviewcompleted`.
3. **Run control** (sidepanel): runs start, pause, resume and cancel under your hand; a cancelled run rolls only its queued steps back while the executed steps stay sealed. Completion event: `runcontrolcompleted`.
4. **Log audit** (dashboardpage): the immutable log chains every step transition with masked values; open the dashboard, verify the chain and copy a verified range as an audit excerpt. Completion event: `logauditcompleted`.

Full completion writes the single consent scoped event `onboardingconsentgranted` with the boundary `onboarding`; the onboardingconsentgate refuses any second consent event of the walkthrough.

## The 1.1.65 finishing elements

The 1.1.65 family finishes the interface with the second half of the surface grammar, all riding the same command bus, audit trail and broadcast channel through the views command family:

| Element | Behavior |
| --- | --- |
| datagrid | The sidepanel data tab previews every extraction result as a grid: the column types infer from the observed values (numbers, booleans, iso dates and text), the sort and the filter run locally inside the surface, and an inclusive row range selects the partial export scope. |
| exportmenu | The csv, json and clipboard formats scoped to the selection, one step or the whole run; the payload writes masked values only, honoring the maskinputs verdicts of every sensitive field shape. |
| quickactions | The context menu family of the active tab (extract page, capture shot, run recent and open dashboardpage) rides the origin allowlist of the clicked tab: only the permitted actions surface, and the popup lists them beside the recent tray. |
| shortcutkeys | Run, pause, resume, cancelrun and the commandpalette bind to user editable combinations in the optionspage; every dispatch passes the palette action gate with its gates intact, and the palette command binds on every surface. |
| omniboxtask | The omnibox keyword parses into a taskinput submission of the omnibox surface and lands in the standard proposal flow with its review intact; the manifest registers no new permission, so the parser serves the surface family entry point. |
| statusbadge | The toolbar badge derives its idle, running, waiting and attention states from the run state and counts the waiting gates, riding the action entry the manifest already declares. |
| notifications | notifydone fires on run completion with a deep link to the runsummary, notifyattention fires on gate waits, phishguard blocks and deferrals with a deep link to the exact waiting step, the os do not disturb state holds the toast while the deep link stays in the history, and a page content body builds only after its consent. |
| recenttray | The popup lists the latest runs with resume for halted runs and reopen for completed ones, inside the user configured depth. |
| pickeroverlay | The sidepanel starts a picker session on the granted origin, lists the element candidates with stability scored selectors and locks one candidate for the proposed step; the guidedtips explain the selector choice and dismiss and recall from the optionspage. |
| targethalo | The active target element carries an outline whose color follows the step state: gray pending, blue running, amber waiting, green done, red failed and dark halted. |
| shotpanel | The capture preview of a step with its provenance and redaction verdicts behind the granted origin gate, with the zoom and pan for the large stitched captures. |
| compareviewer | Every executed write step pairs its before and after captures; the slider overlays the two so the user sees exactly what the step changed. |
| pagechips | Gated steps render inline confirmations anchored to the target element with approve and reject actions whose resolutions write to the immutable log exactly like stepapprove. |
| siteprofiles | Per site theme, shortcutkeys and default view stored beside the originprofiles family, activating automatically on their origin and never adjusting a policy gate. |
| darklight | The theme follows the os preference with a manual override and the siteprofile layer first; the tokens cover every surface including the dashboardpage through shared custom properties. |
| locales | English and portuguese bundles with the english fallback and per language date, number and duration formatting; the a11ylabels follow the interface language. |
| importexport | The settings and data bundles move the originprofiles, siteprofiles, notes and preferences between profiles while secretvault values and unmasked logs never enter any bundle under any flag. |
| dropimport | The optionspage and the dashboardpage accept the csv, json and workflow files the user drops, with the file kind detection naming what the import path takes. |
| featuretour | The onboarding walkthrough replays on demand with added stops for the datagrid, the compareviewer and the pickeroverlay. |
| stetoasts | Step completion confirms with the step kind and its duration, stacking inside the user configured live count with the full history queryable. |

Every element above rides the same consent chain: the quickaction gate (origin allowlist of the clicked tab), the omniboxtask gate (proposal flow), the shortcutkey gate (palette binding), the notification content gate, the pickeroverlay gate (granted origin), the shotpanel gate (captures of granted origins), the siteprofile gate (https origin) and the importexport gate (secrets and unmasked logs refuse in full). See `docs/19.interfaceinventory.md` for the a11ylabel of every control.
