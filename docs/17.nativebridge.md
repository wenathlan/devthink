# 17. Native host bridge

The native host bridge of the 1.1.85 family extends devthink to desktop processes: an **optional** native messaging transport the user installs, consents to per boundary and stops with one press. Nothing native runs until the user installs it — the manifest declares the `nativeMessaging` permission in the optional set only, the deep manifest checks of the cli refuse it in the required set, the transport ships deny by default, and every path, window and bound stays a user choice with no code default anywhere.

## Install walkthrough

1. **Build the companion** with the packaging build: `pnpm build` runs the plain node recipe that compiles the root `companion.ts` with esbuild, stamps the package version over the source build marker and writes `dist/companion.js` — the companion ships as source plus a build command, never as a binary blob.
2. **Record the install consent** in the options page (Native host bridge section): name the host (for example `com.your-domain.devthink`), name the user profile directory the installer writes into, and grant the install consent — the gate explains the scope first: the companion process the manifest launches, the profile directory the manifest writes into and the extension origins the manifest allows.
3. **Write the host manifest** with the reviewed installer: `node dist/cli.js native install --profile <profiledir> --host <hostname> --extension-id <extensionid> --companion <companionpath> --consent true`. The installer fills the generated extension id placeholder of the template, writes into `<profiledir>/NativeMessagingHosts/<hostname>.json` and refuses a system wide install without the explicit `--systemwide true` flag.
4. **Attach the native port** from the options page — the extension opens the runtime native messaging port, the handshake frame rides the wire and the diagnostics report the companion build, the protocol version and the wsbridge port.
5. **Uninstall** with `node dist/cli.js native uninstall --profile <profiledir> --host <hostname>` — the uninstaller removes the host manifest and its preferences, and the extension returns to its deny by default posture.

## Consent model

- **Install consent** (`nativeinstallconsentgate`): explains the scope before any host registration; the installer writes no manifest without the recorded stamp.
- **Transport consent** (`nativetransportconsentgate`): opens the bridge per call class — read, interaction and sensitive stay separate grants, so a read grant never widens into an interaction or a sensitive surface.
- **Surface consent** (`nativesurfacegrant`): the os dialog and notification surfaces each carry their own grant stamp, because a desktop surface never opens from a class grant alone.
- **Human approval** (`nativesensitiveapprovalgate`): a sensitive native call waits for the human approval — the class grant never suffices on its own.
- **Kill switch** (`nativekillswitchgate`) and **escape hatch** (`nativeescapehatchgate`): one press stops every native call instantly; the port detaches, the wsbridge session closes and no frame crosses until the release.
- **Headless posture** (`nativeheadlessgate`): the headless run keeps the transport disabled unless the user configured a host.

Every native call writes an audit record (`nativecallrecord`) with its correlation id, surface, call class and outcome — never a payload — and the `native/call` notification streams to subscribed mcp clients.

## The wsbridge protocol and token model

The wsbridge translates the native port to a localhost websocket server: the companion binds a random free port on the loopback (the zero port asks the socket), mints a per session token and advertises the port and the token to the extension over the native port — the only place the raw token ever appears. The session records keep the sha-256 hash of the token; the logs, the audit entries and the diagnostics reports never carry the raw value.

Frames reuse the servercontract envelopes of the 1.1.82 family: one `eventpost` envelope per native frame with the negotiated contract version, the stable operation id, the multiplexed stream name `nativetransport` and the native frame as the stream payload (the frame carries its kind, its correlation id, its session id and its body). Every incoming frame authenticates against the session token before any body read, a second extension side connection refuses (the wsbridge supports one extension connection at a time) and a quiet session expires after the user configured idle window — an absent window never expires.

The native frames carry correlation ids one run stamps (`run-<seed>-<sequence>`), the origin and session checks validate every frame against the paired session, and the secret exclusion keeps key vault material out of every frame: a body key of the secret shape (`apikey`, `token`, `secret`, `password`, `authorization`, `credential`, `privatekey`) refuses the whole frame, so the native host never receives key vault material.

## The companionbin build recipe

The companion builds inside the packaging build: the plain node recipe of `tests/build.mjs` compiles the root `companion.ts` with esbuild, stamps the package version over the source build marker and writes `dist/companion.js` with its sourcemap, then stamps the host manifest template the companion module embeds into `dist/nativehost.template.json`. No native compiler and no network step — and the packaging build asserts the recipe runs, so a regression in the plain node path fails the build. The companion's own log path and size bound arrive from the launch environment (`DEVTHINKCOMPANIONLOG`, `DEVTHINKCOMPANIONLOGBOUND`) and stay off without them; the log rotates to its `.1` suffix when the bound would pass.

## Diagnostics

`node dist/cli.js native diagnostics` and the options page Diagnostics button read the same report: the install state, the port state (detached, attached or crashed), the hostname, the extension id, the installer version, the companion build and protocol versions, the wsbridge port, the degradation posture, the consent grants and the last errors with their retry hints (`none`, `reconnect`, `reinstall`).

## Graceful degradation

An absent host (nothing installed), an outdated host (another protocol major version — the upgrade path keeps compatibility for exactly one major version) or a crashed host never fails a run: the engine degrades with the transport off and every step runs inside the browser. The heartbeat frames detect the host process liveness under the user configured interval (an absent interval never expires the check), and the extension reattaches on the host restart.
