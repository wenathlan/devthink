# Migration guide

The migration guide records what an upgrader needs to know when moving between devthink releases. Each entry names the release that changed the behavior, who the change touches and what to do; everything else carries over unchanged because the frozen contracts of the 1.1.91 api freeze hold every library surface, protocol message, schema and capability manifest hash stable until 2.0.0.

## Upgrading to 1.1.95 (the security hardening release)

The permission set is stable for every upgrader: the 1.1.95 release adds no permission, removes no permission and reorders none — the diff against the previous release reports zero added, zero removed and none reordered, so an update from any release since 1.1.85 re-prompts for nothing. The whole permission growth history since the 1.1.31 baseline stays in the optional set with a justification row per permission in the permdiff justification table of `docs/01.extensionpermissions.md`, and the audit trail of the installed update records the permdiff with the permission set hash of the release (the transparency page lists it and the update flow never widens a grant silently). An upgrader from before 1.1.85 meets only the optional `nativeMessaging` prompt the 1.1.85 native host bridge declared — the deep manifest checks still refuse it in the required set, so nothing native runs without the per install host registration.

The strict content security policy lands with this release: every extension page now carries `script-src 'self'; object-src 'self'; frame-ancestors 'self'`. No extension page or remote page ever embedded a devthink surface before, so nothing an upgrader built breaks — the only framing the policy allows is the extension's own pages framing each other (the options page embeds the transparency page), which keeps working. An embedding a third party built by loading a devthink page inside a remote frame now refuses by design: the surface belongs to the extension chrome, not to an outer site. Every script, style and connect source stays the package itself, and the cspaudit gate (`node tests/cspaudit.mjs`) verifies the policy set, the built bundles and the single injected file on every release.

Library consumers see no surface change at all: the hardening family of this release ships as its own `dist/hardening.js` entry beside the frozen `dist/index.js` surface, the frozen contracts of `tests/artifacts/apifreeze.json` stay hash stable, and the exports map, the protocol messages, the schemas and the capability manifests carry the same identifiers they carried since 1.1.91. The quarantine entries gain an optional `digest` field (the sha-256 the reviewed flow recorded for the local signature check) and the stdio bridge records gain an optional `clientverified` marker — both additive and optional, so an existing consumer of those records keeps parsing them unchanged.

The configuration surface gains two optional settings and no break: the virus scanning hook accepts a local signature list (hex sha256 digests only — the on device pass answers before any remote endpoint fires) and the purge command accepts a run name for the per run trace purge. Both stay absent by default with the exact prior behavior, and the transparency page now offers the permission rows, the stored data kinds with their purge and export links, the audit integrity result and the masked transparency export beside the grants it already carried.

## Upgrading from the pre consolidation layout (before 1.1.93)

The repository consolidated every browser manifest into the single root `manifest.json` in 1.1.93: the firefox overlay now lives under `browsers.firefox` and the safari overlay under `browsers.safari` of the root manifest, no per overlay version key exists (the root manifest's version is the single source) and the `manifests/` directory is gone. A checkout that referenced `manifests/firefox.json` or `manifests/safari.json` reads the overlay sections of the root manifest instead; the build, the tests and the workflows already do. See the 1.1.93 changelog entry for the full consolidation record.

The kind documentation of `docs/kinddocs.md` covers every action kind of the immutable vocabulary with its consent class and its plan fragment, and the reference documentation of `docs/refdocs.md` mirrors the cli, protocol, audit, configuration, schema, capability, tool, trigger and permission tables — the upgrade path reads both before a migration.

## The release candidate revision (1.1.99)

The first release candidate joins the gate chain: upgraders from any 1.1.x release keep their storage, sessions and settings untouched — the storage schemas stay frozen under the freeze artifact and the permission set stays pinned by the permission diff baseline, so no data migration step exists between 1.1.98 and 1.1.99. The deprecation window of the protocol major one carried the release candidates to the 2.0.0 sunset, which has since closed: the negotiation refuses a version one declaration below the supported floor with the migrateplan command and this guide inside the refusal, and the 2.0.0 release ships the migrateplan command with the automa, selenium, ui vision and tabular importers for plans authored outside devthink (the migration bridge section below records the shipped surface). The full chain from 1.1.31 to this candidate, the migration steps and the frozen protocol guarantees live in docs/releasenotes.md.

## The 2.0.0 protocol major one sunset

The deprecation window that opened at the 1.1.91 api freeze closed at 2.0.0, and the sunset removed both fields the window carried. The protocol line now speaks major two only: a client that declares no protocol version answers the frozen default of two, a client that declares major one refuses below the supported floor with this guide inside the refusal, and the client capability set of the mcp surface declares the numeric `protocolmajor` — the full version string the version one clients exchanged parses nowhere. Unknown fields refuse on every protocol major the line accepts, and the umd envelope exposes the lowercase `devthink` global only, so a script tag that still reads the uppercase `Devthink` global meets an undefined reference.

Version one assets convert forward rather than break: run the migrateplan command on a version one plan to convert it into a protocolv2 plan, bring automa, selenium, ui vision or tabular automation assets through their importers — every importer converts first and never executes anything outside the normal consent gates — and keep the storage, the sessions and the settings as they are, because the frozen storage schemas and the permission baseline carry them across the major line unchanged. `docs/deprecation.md` records the executed sunset with the window history.

## The 2.0.0 migration bridge (migrateplan)

The 2.0.0 release ships the migrateplan command with the migration tooling the roadmap 1.1.92 section promised and the 1.1.99 candidate deferred with a written record: `devthink migrateplan <source> --format <v1|automa|selenium|uivision|tabular>` converts one foreign plan source into the reviewed plan file grammar, the `--out <file>` flag writes the converted plan to its destination while the default prints the plan json to stdout, and the command runs the same lint engine `planlint` runs over the converted plan before anything is written — a conversion that fails its own lint refuses with the schema error exit code instead of shipping a plan the review would reject. Example fixtures of every source format live under `tests/code/importers` (the build copies them into `dist/fixtures/importers`): `v1-plan.json`, `automa-workflow.json`, `selenium-side.json`, `uivision-macro.json` and `tabular-plan.csv`, each beside a refusal twin — `v1-unknown.json`, `automa-unknown.json`, `selenium-unknown.json`, `uivision-unknown.json` and `tabular-unknown.csv` — that carries the one entry its importer refuses.

```sh
node dist/cli.js migrateplan dist/fixtures/importers/automa-workflow.json --format automa --out converted-plan.json
node dist/cli.js planlint converted-plan.json
```

Every imported step maps onto the reviewed plan step grammar: the kind comes from the action kind catalog, the target lands as a reviewed css selector, the value and the reviewed json options ride their frozen fields, and every kind that grades sensitive carries the explicit gate declaration the review demands. The version one grammar carries its `action`, `selector` and `value` fields that move onto `kind`, `target` and `value` — the version one vocabulary and the frozen vocabulary share their kind names, so a legacy action maps directly — its `milliseconds` field lifts a hardcoded wait onto the reviewed delay option grammar, and a source that already parses as the current plan grammar passes through unchanged, so converting an already converted plan yields the same plan. The automa block table maps newtab onto tabcreate, click-element onto click, forms onto fillform, go-back onto back, close-tab onto tabclose, wait onto the delay option grammar, scroll onto scroll and screenshot onto shotview. The selenium command table maps open onto navigate, click onto click, type onto type, sendKeys onto appendtext, select onto select and pause onto the delay option grammar. The ui vision command table maps open onto navigate, click onto click, type onto type and verifyText onto waittext. The selenium and ui vision locators accept the `css=`, `id=` and `name=` prefixes onto the reviewed css selector grammar, the tabular source reads its `# goal:` and `# origin:` preface beside its step, target and value columns, and one plan addresses exactly one origin — the plan origin derives from the side file base url, the first newtab url or the first open target, and a navigation away from that origin refuses.

The refusal semantics stay honest: an unmapped automa block type, an unmapped selenium or ui vision command, a kind outside the reviewed catalog, a locator outside the accepted prefixes, a field without a destination or a source that parses no json refuses the whole conversion with the source entry named — never a silent drop, never a guessed kind. The automa trigger block converts to no plan step: it lands in the conversion report as the paused trigger the scheduler arms only after the plan review.

The provenance and consent posture closes the loop this guide promised: the frozen plan file grammar carries no metadata field, so the source format, the source version, the import date and every field mapping note ride the conversion report the command prints on stderr while the plan json stays grammar-clean. Every importer converts only and never executes anything outside the normal consent gates: an imported plan enters exactly the same review flow, consent gates and origin grants a hand authored plan enters, and no imported plan inherits a consent grant from its source format — the devthink-native grants of a version one plan pass through because they are devthink origin declarations of the same grammar family, never foreign consent grants.

## frequently asked upgrade questions

This faq chapter answers the questions candidate upgraders ask most; every answer restates a guarantee a chapter above records, so the chapter and the chapters it cites say the same thing.

**what happens to my version one plans when i upgrade?** they stop parsing: the 2.0 line speaks the protocol major two plan grammar only, so a plan authored in the version one grammar refuses at its review with this guide inside the refusal — the store itself never breaks on it. the migrateplan command converts one at a time: `devthink migrateplan <source> --format v1` walks the version one `action`, `selector` and `value` fields onto `kind`, `target` and `value` (the version one vocabulary and the frozen vocabulary share their kind names, so a legacy action maps directly), lifts a hardcoded `milliseconds` wait onto the reviewed delay option grammar, and passes a source that already parses as the current plan grammar through unchanged — converting an already converted plan yields the same plan.

**where do the importers live?** the cli carries the command and the importer tables (`dist/cli.js`, `devthink migrateplan <source> --format <v1|automa|selenium|uivision|tabular>` with the `--out <file>` flag writing the converted plan while the default prints it to stdout), the example fixtures of every source format live under `tests/code/importers` in the repository and ship as `dist/fixtures/importers` in the packages, and each fixture sits beside its refusal twin — `v1-unknown.json`, `automa-unknown.json`, `selenium-unknown.json`, `uivision-unknown.json` and `tabular-unknown.csv` — that carries the one entry its importer refuses.

**do my stored sessions and memory survive the upgrade?** untouched: the storage schemas stay frozen under the 1.1.91 freeze artifact and the permission set stays pinned by the permission diff baseline, so no data migration step exists between 1.1.98, 1.1.99 and 2.0. the five session stores keep their storage keys (`sitenotes`, `scratchpad`, `runsummary:<runid>` with `runsummaryindex`, `corrections`, `consentmemory`), their per record provenance, their retention windows and their gates (the full model is `docs/17.memorymodel.md`), and the settings carry across the major line unchanged.

**can a version one client still connect after the upgrade?** no. the protocol floor is major two — `version.ts` pins `protocolfloormajor = 2` — so a client that declares no protocol version answers the frozen default of two, and a client that declares major one refuses below the supported floor with this guide and the migrateplan command inside the refusal. the client capability set of the mcp surface declares the numeric `protocolmajor`; the full version string the version one clients exchanged parses nowhere, and the deprecation window that carried version one tolerance closed with the 2.0.0 sunset (see the sunset chapter above and `docs/deprecation.md`).

**what does the review flow require after a migration?** exactly what a hand authored plan enters: an imported plan passes the same review flow, consent gates and origin grants — the command runs the same lint engine `planlint` runs over the converted plan before anything is written, a conversion that fails its own lint refuses with the schema error exit code instead of shipping a plan the review would reject, every kind that grades sensitive carries the explicit gate declaration the review demands, and one plan addresses exactly one origin (a navigation away from the derived origin refuses). the automa trigger block converts to no plan step: it lands in the conversion report as the paused trigger the scheduler arms only after the plan review.

**does consent history carry over?** the devthink side does, and the foreign side never exists. the consent memory records — every grant, denial, expiry and revocation with its boundary and kinds — keep their per profile workspace scope and their storage key across the upgrade, the per origin automation allowlist and the originprofiles persist in extension storage, and the advisory posture stays advisory: no entry auto grants and a denial weighs the same as a grant. no imported plan inherits a consent grant from its source format; the devthink-native grants of a version one plan pass through because they are devthink origin declarations of the same grammar family.

**will the upgrade re-prompt for permissions?** no: the permission set stays stable for every upgrader — the 1.1.95 release added no permission, removed no permission and reordered none, so an update from any release since 1.1.85 re-prompts for nothing, and the audit trail of the installed update records the permdiff with the permission set hash of the release (the transparency page lists it). an upgrader from before 1.1.85 meets only the optional `nativeMessaging` prompt the 1.1.85 native host bridge declared — the deep manifest checks still refuse it in the required set.

**do i need to convert my plans before upgrading?** no. the storage, the sessions and the settings carry across the major line unchanged, and the migrateplan command ships in the 2.0 line itself, so conversion happens whenever a version one plan is next needed. a plan that sits unconverted refuses only at its own review, never at the store.

**what happens to a script tag that reads the umd global?** the umd envelope exposes the lowercase `devthink` global only, so a script tag that still reads the uppercase `Devthink` global meets an undefined reference. the umd example page (`dist/umd-example.html`, derived from `tests/code/umd.html`) shows the working reference.

**what if the importer refuses my source?** the refusal is the guarantee, never a silent drop and never a guessed kind: an unmapped automa block type, an unmapped selenium or ui vision command, a kind outside the reviewed catalog, a locator outside the accepted `css=`, `id=` and `name=` prefixes, a field without a destination or a source that parses no json refuses the whole conversion with the source entry named. the refusal twins under `tests/code/importers` demonstrate every refusal class, and the failed conversion answers with the schema error exit code the cli documents (`3` in the exit code table of `docs/configuration.md`).

## the rollback path from a candidate install

the store channel moves only through the operator's hands: the release workflow publishes the registries and the github release, never the web store — the store submission stays the operator-published posture the readiness review records among its residual risks — so the store listing keeps serving the last operator-submitted package until the operator submits the 2.0.x package, and a return on the store is the same operator action in reverse. the release assets keep every published version: the github release page of `wenathlan/extension` carries `Devthink X.Y.Z` with `devthinkX.Y.Z.zip` per release (the chromium zip, the firefox xpi, the safari skeleton zip and the npm tarball beside them, all under the `SHA256SUMS.txt` the manifest covers), so the 1.1.99 zip stays downloadable after the 2.0.x release publishes, and it loads the same way the cross browser smoke walkthrough of `docs/cross-browser-smoke.md` documents (unpacked in dev mode, or the unpacked `dist/` directory of the 1.1.99 checkout directly).

the data story stays honest about the platform. the frozen storage schemas and the permission baseline carry the store across the major line unchanged — no data migration step exists in either direction — but the chromium platform drops an extension's `chrome.storage.local` when the user removes the extension, so the durable rollback exports first and reinstalls after. the export surfaces the extension ships are the durable copy: the sessions export writes the format version, the record ids, the byte size and the checksum (an import parses only when the format version, the record id list and the checksum all verify before the full record review), the audit bundle export ships the notes, the summaries and the corrections with the sealed bodies intact, the transparency export returns the whole transparency report through the masking and redaction pass, and the library manifest list exports for audit with no step payload.

the sequence: export what matters (the session file, the audit bundle, the transparency report) from the candidate while it still runs, remove the 2.0.x install (the `chrome://extensions` remove control or the store uninstall — either path clears the extension storage with the install), install 1.1.99 from the kept release zip or from the store once the operator republishes it, import the session file through the full record review, and re-grant the origins: the denydefault posture refuses every origin the user never granted, so the allowlist and the originprofiles re-enter through the same prompts a fresh install enters, while the consent memory records ride the import only as advisory history — no entry auto grants.

the honest limits: a 2.0-written store read by 1.1.99 is best effort. the store keys and the record families stay the frozen shapes both releases share, so the sessions, the notes, the run summaries, the corrections and the consent memory a candidate wrote load in 1.1.99 where the storage survived — an unpacked load of the 1.1.99 dist over the same extension id replaces the build without the removal, which is the one path that keeps the store whole. anything a 2.0-only surface wrote rides the stored record unrecognized: the 1.1.99 accessors list what they know and never rewrite what they do not, the sealed run logs verify under the same loghash chain both releases carry, and an import file whose format version moved refuses rather than guesses. the version one plans converted under the 2.0 migrateplan command lint under 1.1.99 too because the plan file grammar is frozen contract; the foreign sources re-convert with the 2.0 cli alone (`dist/cli.js` is library surface independent of the installed extension, so the migrateplan bridge keeps working beside a rolled back install), and the paired remote clients survive the rollback because both releases speak protocol major two since the 1.1.91 freeze.
