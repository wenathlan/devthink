# Release and Publication Architecture

`package.json` is the sole version source. A `main` push that changes it or `CHANGELOG.md` begins the release workflow, which synchronizes all derived metadata and renders `docs/releasenotes.md` from the matching changelog section before resolving an immutable `vX.Y.Z` tag. The package remains `@wenathlan/extension`; the repository is `wenathlan/extension`.

## Trigger matrix

| Trigger | Result | Publication |
| --- | --- | --- |
| Pull request or main push | **verify** runs type checks, tests, metadata checks, package preview, extension ZIP generation, actionlint and artifacts. **security** runs code scanning, dependency review for pull requests, secret scanning, SBOM generation and dependency audit. | None. |
| `package.json` or `CHANGELOG.md` changed on `main` | **release** synchronizes derived metadata/isolated notes, creates a missing immutable tag, invokes verification, assembles all assets, publishes registries and creates or updates the GitHub Release. | GitHub Release, GitHub Packages npm/Maven/NuGet, npmjs and GHCR. |
| Tag `vX.Y.Z` or controlled manual dispatch | **release** validates a matching existing source and runs the same artifact/publication chain; it never moves a mismatched tag. | Same compatible targets. |
| Weekly schedule or controlled manual dispatch | **maintenance** detects current stable direct dependencies from npmjs, Node from the official release index, npm and Bun from npmjs, pnpm, and mutable action tags from their official releases. It opens/refreshes a reviewable pull request for non-breaking changes only. Major and `0.x`-minor transitions require `allow_major_updates=true`. | Never merges, tags, releases or publishes. |
| Successful security run or daily schedule | **maintenance** removes bounded stale caches: non-main caches older than 24 hours and `main` caches beyond the retention limit. Manual use defaults to dry-run. | No package publication. |

Maven remains a descriptor rather than a Java runtime API. NuGet remains a distribution package rather than a browser-control .NET API. These boundaries prevent registry coordinates from overstating the runtime capability of the extension.

## Completed legacy NuGet migration

The one-time `migratelegacynuget` job completed during v1.1.12, deleting only the superseded `Wenathlan.Devthink.Extension` package after an exact-name, exact-namespace preflight. The current `extension` NuGet package, all version tags and all other registries were excluded. As of v1.1.14, the job and all package-deletion commands have been removed from the repository: future release tokens have no reason to carry that destructive capability.

GitHub documents that external GitHub Packages administration uses a classic personal access token, whereas a workflow token can delete a package associated with its repository when it holds package-admin access. That bounded migration is now historical evidence, not a continuing release capability. [1] [2]

## Safety, provenance and attribution

Artifacts are aggregated and checksummed before the GitHub Release is created. The manifest excludes itself and records sorted bare filenames, allowing `sha256sum --check SHA256SUMS.txt` directly after all release assets are downloaded to one directory. This behavior was independently verified against the full public v1.1.13 asset set. Node 26.8.1, npm 12.0.2 and Bun 1.4.0 have dedicated bounded compatibility declarations and checks; pnpm 11.24.0 remains the canonical lockfile tool. Because Node 26 images no longer include Corepack, the container derives and explicitly installs npm and pnpm from the checked-in package metadata before frozen-lockfile installation. The container digest comes directly from the push result and is attested. All workflows are parsed locally as YAML 1.2 and checked for required controls; verification also uses a commit-pinned actionlint wrapper. The release commit uses `Nathlan Bros <263045985+wenathlan@users.noreply.github.com>` for both author and committer. GitHub Actions records its own workflow actor separately, so commit attribution and push-transport identity remain distinct.


## Cli smoke step of the verify chain (1.1.80)

The validate script chain runs the expanded cli smoke step beside the manifest gate: `node dist/cli.js help` verifies the command surface answers after every build, the verify workflow runs `planlint` over every example plan in the `dist/fixtures/plans` build artifacts and `runworkflow` in dry run mode over the emitted example workflows, and the release workflow packs the staged flat package (`npm pack distpackage`) so the published tarball carries the library surface at the package root — one file per correlated domain with the caps, schemas and fixtures groups beside it, no path nested past two directories — and the fixtures ride the `fixtures/` group of that package so the published samples sit where the commands document them. The containerfile runs the manifest command as an install sanity check and one fixture through headlessmode as a container smoke step.


## Multi runtime verification matrix (1.1.81)

The verify workflow runs the build matrix under node, bun and deno: a require smoke against `dist/index.cjs`, an import smoke against `dist/index.js`, a global smoke against `dist/devthink.umd.js`, a deno check over the deno entry and the vitest suite once under bun. The release workflow attaches the umd bundle and the declaration bundle as release assets beside the existing set, the containerfile verifies the cjs entry with a require call, and the bundle size budget asserts per target limits (index 1800000b, indexcjs 1900000b, neutral 1800000b, umd 1900000b, node 1900000b, bun 1800000b, deno 1800000b, policy 600000b, protocol 380000b, memory 330000b, progress 60000b, cli 600000b, headless 700000b) so an oversized bundle fails the build before it ships.

## The mcp ci checks (1.1.84)

The mcp transport coverage rides three lanes: the containerfile smoke boots the self hosting runner, starts the mcp server listener as its child process and answers a json rpc ping against the http listener (the `--check` mode the container build runs as a build check), the vitest suite covers the stdio transport in process — the mcp stdio bridge tests drive the bridge launch, the frame relay in both directions, the process restart, the platform client verification and the frame routing over the stdio and http transports — and the mcp client example of `tests/code/mcp-client.mjs` ships in the packages as `dist/fixtures/mcp-client.mjs` for a manual stdio walk, with no ci step running the example script. The bundle size accounting covers the mcp bundle, the naming check keeps it free of underscored identifiers, and the npmgate check allows the mcp bundle in the tarball.

## The publishing pipeline chain (1.1.87)

The release workflow publishes a package for every mode in one chain: the channel jobs (githubpackages, npmjs, maven, nuget, container, digest, vsix, firefox and site) each gate on the assemble job, every publish retries inside a bounded three attempt policy with a growing pause, and the attestation job runs after every channel job. The maven job deploys one module per consumption mode and retains the module jars and the aggregator pom as release assets; the nuget job packs the richer distribution (the cli, headless and mcp content files, the umd and cjs bundles, the declarations, the fixtures and the readme) and publishes it; the container job pushes the multi stage image with the version tag beside the `stable` channel alias and attests it; the digest job inspects the pushed image, verifies the stable alias tracks the same digest and publishes the digest files; the vsix, firefox and site jobs verify their channel artifacts (the marketplace metadata check for the vsix, the manifest placement for the xpi, the index page and cache headers for the site) before the artifacts attach.

The sbom job generates the cyclonedx inventory over every release artifact through the `sbom` module the tarball ships, the attest job creates the provenance attestations through the workflow identity (no signing key material lives in the repository — everything rides the oidc token of the run or repository secrets) and writes the attestations record, and the releaseassets job emits the artifact manifest that lists the name, the byte size, the sha256 checksum and the publishing channels of every artifact beside the checksums file. The registry jobs and the github release require the `release-approval` environment protection, so nothing auto-publishes when the operator configures the environment with reviewers. The github release gathers every artifact into a draft first, the verification step downloads every draft asset back and verifies the checksums, and only the verified release publishes; the release notes carry the per channel artifact sections that record every artifact of the release. The version sync step stamps the same number into package.json, the root `manifest.json`, the pom, the csproj and every maven module pom, and the overlays — the vsix packaging overlay and the per browser overlays under the `browsers` key — live inside the root manifest and carry no version of their own, so no drift between the manifest files is possible; the check mode verifies zero drift across every packaging file. The verify workflow runs the vsix package build, the nuget pack dry run, the maven pack dry run, the container image build with its smoke and the artifact manifest check against the built set; the maintenance workflow updates the version catalog of docs/runtimeversions.md after each release through the same synchronization; the full channel and artifact map is documented in docs/19.distribution.md.
