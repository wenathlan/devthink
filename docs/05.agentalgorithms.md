# Browser Agent Algorithm Evidence

The implementation will model a browser task as a finite, reviewable sequence: intent, bounded observation, action proposal, user-policy decision, execution, fresh observation and outcome record. This is intentionally different from an unrestricted loop that can repeatedly invoke tools without a user-visible state boundary.

| Design area | Evidence | Devthink 1.1.1 decision |
| --- | --- | --- |
| Observation | WebArena evaluates URL, focused tab and page content represented as HTML, screenshots or the accessibility tree; its analysis presents the accessibility tree as a more compact structured representation. [1] | Use semantic observation first, with a bounded text/role snapshot; screenshot capture is optional and requires separate session approval. |
| Grounding | WebArena describes element identifiers obtained from DOM or accessibility-tree traversal, which make a target action explicit. [1] | Tool proposals carry a target reference plus a human-readable label. A target reference expires after navigation or document mutation. |
| Multi-tab control | WebArena models tab focus, tab creation and tab closure independently from page actions. [1] | Treat tab selection and new-tab navigation as separate, auditable tool classes. Closing a tab is always treated as a sensitive action. |
| Evaluation | BrowserGym provides a framework and several benchmarks for implementing and evaluating web agents. [2] | Maintain deterministic test fixtures and action traces instead of scoring an agent only by a claimed final answer. |
| Multimodal fallback | Chrome guidance explains that DOM, accessibility tree and screenshots provide complementary signals; screenshots are slower and more expensive for agents. [3] | Choose accessible semantic data by default, fall back to a screenshot only when the user has approved visual capture and the structured view is insufficient. |

The public WebArena study reported that its best GPT-4-based agent achieved a 10.59% end-to-end task success rate in its benchmark at the time of publication. This is not a performance estimate for Devthink; it supports the product requirement for checkpoints, failure recovery and a reviewer-controlled boundary before consequential actions. [1]

## Pointer paths, retry rules and the numbered clickable map since 1.1.33

WebArena grounds element identifiers in dom or accessibility tree traversal and treats grounding failures as a first class error source. [1] Devthink 1.1.33 answers both observations with three reviewed algorithms.

Pointer paths model pointer travel as a reviewed `pointpath` between a start and an end point through optional waypoints, shaped by a reviewed `speedprofile`. The bridge interpolates the path into settle delimited hops: each leg is divided at the base cadence, the reviewed easing (`linear` or `easeinout`) distributes progress across the leg, the reviewed peak velocity in pixels per second caps the speed of every hop (the hop delay rises whenever the distance over peak velocity exceeds the base cadence, and a reviewed duration never overrides the peak), and the reviewed jitter window adds a bounded random settle before each dispatched `pointermove`. `pointerover` opens the path and `pointerout` closes it, so pages observe a complete enter move exit sequence instead of a teleport.

Retry rules absorb pages that move under the pointer. A `retryaction` step wraps another reviewed step by sibling step id or inline definition and carries a `retryrule` of attempts, settle window and movement tolerance; the attempt count is a reviewed choice with no code ceiling. After each failed attempt the loop waits the settle window, re-probes the target geometry and compares the movement delta against the tolerance: a target that stayed within tolerance stops the loop early (retrying cannot help), a moved target earns another attempt, and every outcome records the attempts made and the largest movement observed for the audit trail and the step timeline.

The numbered clickable map turns `mapclicks` into a stable addressing surface: every clickable element on the page is numbered in document order with its selector, role and label, and the map is stored under a fresh observation version. Numbers stay stable inside one observation version, an `index` mode targetref resolves a map number back to the element, the review panel renders the numbered list beside the plan, and the user can click an entry to record it as the target hint for the next plan input. Resolution summaries per target mode are stored alongside, so later selector derivation can learn from what the user actually approved.

## List, table and banner detection heuristics since 1.1.34

Devthink 1.1.34 gives the agent every way to see a page, and three of the new detectors answer the recurring structure questions of agent benchmarks: where the repeated items are, what a data table means and which consent banner blocks the task. All three run read only behind the same session and approval gates.

List detection samples sibling structures instead of guessing containers: for every element with two or more children, the detector groups the children by their tag plus sorted class signature, and a group of at least two siblings that carries text becomes a `listpattern` with its container selector, an inferred shared item selector (tag plus class suffix) and the text samples of each item. This infers the repeating unit from the page itself — the same grounding WebArena asks of dom traversal — without hardcoding any site vocabulary, and the side panel offers each detected list as a plan suggestion the user can pick as a target hint.

Table detection normalizes real `<table>` structures into a `tableshape`: the first row carrying `<th>` cells becomes the header row, every later row is body, column specs are built per column with the header label (or a positional `column n` label for headerless tables) and the count of non-empty cells, and the `<caption>` is kept when present. Pagination counting reads the entries a page itself renders inside navigation, footer or pagination-classed containers: numeric entries collect into the page set, `aria-current="page"` and current-classes mark the current page, and the total is estimated from the largest number seen, so `countpages` reports what the page claims rather than crawling.

Banner detection matches consent banner shapes against a locale spanning keyword vocabulary (cookie, consent, gdpr, lgpd, privacy, ccpa) over candidate containers found through banner-shaped id, class and dialog selectors; nested candidates collapse into their outermost banner, a candidate needs either text or controls to count, and each match becomes a `bannerreport` with its kind keyword, selector, text and the labels of its buttons and links. `watchbanner` polls the matcher for the reviewed lifetime so late mounting banners are still caught, every report lands in the per session banner stream, and the review panel shows a banner review card before any interaction — the agent proposes the click, the user reviews which consent control it belongs to.

## Spa routing, rate limits and trail audit since 1.1.35

Devthink 1.1.35 gives the agent navigation mastery, and three of its algorithms answer the recurring navigation questions of agent tasks: how to route a single page app without a reload, how to stay polite against one domain, and how to prove afterwards where the session actually went.

Spa routing treats a url change inside one origin as a route change rather than a load. The classifier compares the previous and current url with the tab status: a change with a loading status is a full load, a change without one is a `route` (history pushState or replaceState), and an unchanged url with a loading status is a reload. `spanav` clicks the reviewed control and then waits for the route change, optionally bounded by a reviewed `routepattern`; `spawait` waits for the url change without clicking, listening for popstate and hashchange while polling the url as a fallback, because the isolated world cannot intercept history pushState calls made by the page itself. Route changes observed by the background watcher append to the navigation trail of the session even when no step drove them, so the trail stays the honest record of where the tab went.

Rate limits are per domain windows whose size and ceiling are always the reviewed choice: a `navrate` step installs a `ratelimit` of domain, window and ceiling, the window state (openedat and hit count) persists in local storage across service worker restarts, and every navigation the background performs — container opens, navlist entries, link following, batch opens, clipboard opens — first asks the live window. When the count reaches the ceiling inside the window the navigation is refused with the retry delay; when the window has elapsed the state resets and the navigation proceeds. No code ceiling exists anywhere in the math: a plan may review a window of one minute and a ceiling of three, or a window of one day and a ceiling of one hundred thousand.

The navigation trail is the audit backbone of the whole family: every completed navigation appends a `trailentry` with the url, the tab title, the step ref that drove it and the timestamp, `trailaudit` restores the trail for review, `navintent` records what the plan intended so intent and outcome can be compared later, and redirect chains assemble from the tab update transitions into hops with statuses and timing whose final url `readfinalurl` reports. Together the trail, the intent records, the rate windows and the curated batch verdicts let a reviewer reconstruct not just what the agent did but whether it stayed inside the origins, the pace and the curation the user approved.

## Tab watchers, layouts and session snapshots since 1.1.36

Devthink 1.1.36 gives the agent command over the whole browser surface, and three of its algorithms answer the recurring questions of multi tab tasks: how to observe tabs instead of pages, how to preserve a working arrangement, and how to prove what a run actually touched.

Tab watchers observe the browser instead of the dom. A `watchtab` step registers a lifetime window like the page watch kinds, and the background tab event listeners (title updates through tabs onUpdated, activations through tabs onActivated, closures through tabs onRemoved) feed every live registration with a persisted `tabwatchevent` stream; the step result carries the events observed inside its window, the registration survives service worker restarts and is reconciled on restart exactly like the page watches, and the reviewed event filters can narrow the stream to title, activation or closure events.

Layouts capture arrangement instead of urls alone: `savelayout` builds a `tablayout` from the live tab set, the stored group registry and the live window bounds, and `restorelayout` replays only the urls that are not already open, so restoring never duplicates what survived. Group membership is registry math: moves reorder member ids from the live tab order, renames keep color and collapse state, and closed members drop out. Session snapshots wrap the same layout in a `sessionsnapshot` with a session ref, so `snapshotsession` freezes the full surface of a run and `reopenrun` brings back a previous run without reopening tabs that are still open.

The budget and badge algorithms keep consent visible: the concurrent task tab count is graded against a user configured ceiling only (`tasktabgauge` refuses nothing when no ceiling is set, and no code ceiling exists anywhere), badges refresh from the live progress state of each task tab (`badgefromprogress` renders `n/total` or `done`), and the popup badge counts the tabs with active tasks beside the queued navigation targets, so the user sees the surface the task actually occupies.

## Wizards, dependent controls and retry loops since 1.1.37

Devthink 1.1.37 turns filled pages into structured form work, and three of its algorithms answer the recurring failures of naive form automation: multi step wizards that need per step state, dependent controls that reload their options after a parent choice, and submissions that fail and need a bounded retry.

Wizard tracking is incremental state: a `wizardstate` carries the step index, the total steps and a per step completion flag list, `wizardadvance` marks the executed step's completion signal and clamps the index at the total, progress records each executed step as an outcome with the step index over the total, and the wizard completion share is executed steps over total steps — so the side panel renders step indicators and the plan closes only when every reviewed step, wizard or not, has executed.

Dependent controls wait on evidence, not time alone: `selectchain` records the child select's option count before the parent selection, selects the reviewed parent option through the native setter with input and change events, then polls until the child option count changes (`dependentloaded` compares counts, because dependent selects replace their option list on load) inside the reviewed wait window. Typeahead picking follows the same evidence rule — the reviewed entry must appear in the suggestion list before it is clicked, and the pick is recorded with its query for audit. Calendar picking plans navigation as arithmetic: the month delta between the widget's visible header and the reviewed yyyy-mm-dd date decides how many next or previous clicks precede the day cell click, which works for the common widgets and stays a documented heuristic rather than a widget protocol.

Submission retries are bounded by review, never by code: a `retryform` step carries a reviewed backoff rule with a positive wait window and a growth factor of one or greater plus an optional attempt count, `backoffwaits` expands the windows (wait, wait times factor, and so on) with no ceiling anywhere, and the executor resubmits through the owning form only after the asksubmit ticket was approved, sleeping the reviewed windows between failed attempts. Failed submissions feed the correction loop: `readerrors` associates each validation message with its field through the aria describedby ref first and the sibling text next, the error report is stored per form, and the side panel renders the field refs so the next fill can target exactly the fields the page rejected.

## Pagination, dedupe, merge and resume strategies since 1.1.38

Pagination follows evidence rather than fixed sleeps: the follower resolves the next control as the numbered entry after the current one (or a next word control such as next, > or ›), clicks it, then polls the table until the row set contains a row the previous page did not carry (freshness compares whole row shapes, so reordered rows do not fool the wait) inside the reviewed wait window; pages merge by aligning columns across every extracted page, unioning column keys in first-seen order and filling gaps with empty values, and the loop stops early when no next control remains even before the reviewed page count is reached.

Dedupe and transforms are reviewed, not heuristic: `deduperows` hashes every row over the reviewed key list (an empty key list hashes every column) with the same djb2 style hash used elsewhere in the vocabulary and keeps the first occurrence of each key set, reporting the removed count; `transformvalues` applies one reviewed expression per rule (trim, upper, lower, number, prefix, suffix, replace:from=>to) to the joined source column values, and an unsupported expression surfaces as a per rule error while the original values stay untouched, so a bad rule never corrupts the dataset.

Resume is cursor arithmetic: an extract session records the pages visited, the rows collected and the cursor of completed pages; `resumeextract` reads the stored cursor, steps the reviewed next control forward from the first page (the natural state after a reload) and appends the fresh rows to the same dataset, while a stream state records chunk and written row counters so a restarted service worker continues the stream from the first unwritten row. Provenance closes the audit loop: every export keeps its source url, step ref, row range and deterministic checksum, so an exported artifact can always be traced back to the exact rows, step and page it came from.

## Batch queues, scan hooks and cleanup sweeps since 1.1.39

Batch downloads are a state machine, not a fire and forget loop: each reviewed url becomes a queued record, the executor starts a wave of at most the user configured concurrent window (an absent window never blocks), each started download awaits its settled state through the downloads api search surface, and every transition walks the reviewed table — queued to running, running to paused, paused to running, running or queued to complete or failed — while impossible transitions (pausing a queued file, completing a paused one, reviving a finished one) are refused outright. Progress is files completed over total, one outcome per settled file, so the side panel queue renders live per file states with pause, resume and verify actions.

Mime interception is pattern math with a deny default: a reviewed `mimefilter` carries include patterns, exclude patterns and the default for unlisted mime types; matching checks exclude first (a match refuses), then include (a match reroutes into `devthink-quarantine/`), and everything unlisted follows the default, so an armed deny default cancels unlisted downloads while the filter only applies inside the session origin grants and never to downloads the extension itself started. Scan hooks are endpoint verdicts, not guesses: the quarantined record (id, path, reason) is posted to the configured HTTPS scanner endpoint, the `{verdict}` response maps to pending, clean, flagged or error, and anything absent, malformed or failed stays pending — a hook failure never releases a file, and only the clean verdict opens the release gate that the user confirms per file.

Cleanup sweeps are planned, not destructive by default: the sweeper builds the artifact inventory (exported artifacts with their content sizes, run store artifacts with their capture times), applies the reviewed rules (an age window with no code ceiling, an artifact kind or any, and a keep policy of none, latest or all), and removes only what the plan marks — the keep latest policy holds the newest artifact of each aged kind, keep all holds every aged artifact, and every artifact referenced by an open review card (an attachfile step of the approved plan that has not executed) stays regardless. Capture naming closes the file story: consistent filenames stamp from task, step and sequence parts with per task counters that persist across steps, so every capture of a task lines up in one naming scheme.

## Stitching, blending and state pairing since 1.1.40

Full page capture is tile arithmetic: the stitch plan divides the scroll geometry into a tile grid of scroll offsets where each tile advances the viewport height minus the reviewed overlap rows and the last tile clamps to the page end, the stitching scroll budget of tiles times the settle window must fit inside the reviewed wait window or the step refuses outright, and every tile waits the reviewed settle time after the scroll so lazy content settles before the shot. The seam math is a linear cross fade: the overlap band blends the previous tile content with the new tile row by row using weights that ramp from zero to one, so the first row keeps the existing content and the last row adopts the new tile; a repeated fixed header is detected by sampling the top band of each tile and comparing it against the first tile, and matching bands are skipped so a header renders exactly once (headers taller than the reviewed overlap can still repeat — the honest limit of the band match).

State pairing is a policy, not a step: the capture policy of the run (off, manual, annotated or beforeafter) decides whether every page moving action is wrapped with a before shot and an after shot, and the pair builder refuses a pair when either shot is missing — a failed action skips the pair entirely, while a successful action links both shots with the action kind, the target selector and the dom snapshot id of the same moment, so every state change carries pixel evidence beside the structural diff. Capture naming extends the 1.1.39 counter rule with the capture kind segment, and the sequence counter guarantees uniqueness inside a run across steps and plans.

## Traffic rules, rate limits and upload streaming since 1.1.44

The url pattern grammar is origin arithmetic: a pattern must name its https origin before any path matching happens, then a single star matches within one path segment and a double star matches across segments, so `https://api.example/v1/*` covers one segment below v1 while `https://api.example/v1/**` covers the subtree — patterns without a named origin are refused at validation, in the proposal parser and at execution. Rule sets are run scoped: registration replaces the previous rule of the same pattern, hit counters count matched requests, and reversion is idempotent with the hit counter frozen — the run end, a failure, a cancellation and the manual revert button all route through the same reversion that stamps one revert time and audits every reverted rule with its origin. Header rewriting is ordered application: set overwrites, append joins with a comma (or starts the header when it was absent) and remove drops the header, and every applied rule returns as provenance for the audit trail while unmatched rules cost nothing. The rate limiter is window arithmetic: a reset header value beyond the read time counts as epoch seconds and a smaller value as seconds remaining, the wait is the distance to the reset window clamped at zero, and the reviewed wait budget must cover the wait or the submission refuses outright — both bounds stay user choices with no code ceiling; retry after parsing honors seconds values and HTTP dates of 429 and 503 responses only. The oauth flow is state arithmetic: the consent url carries a run scoped state token, the code capture accepts only redirects on the granted redirect origin with the matching state, provider error redirects fail with their reason, the exchange posts the grant type, code and redirect uri urlencoded to the provider token origin, and the refresh grant posts only the refresh token to the same origin so refresh tokens stay scoped to their provider. Form encoding percent encodes UTF-8 bytes with the unreserved character set of the urlencoded grammar, and multipart streaming emits one chunk per field part, file part and the closing boundary so the payload moves chunk by chunk with the chunk and byte progress reported to the run view instead of buffering the whole body.

## Spam detection and log rotation since 1.1.45

Spam collapse is window arithmetic: identical messages of the same level and source inside the reviewed spam window collapse into one entry carrying a repeat count, the flagged patterns are the collapsed entries whose repeat count exceeds the reviewed collapse threshold, and every bound — the pattern, the window size and the threshold — stays a user configured value with no code ceiling; entries outside the window or differing in level, source or text never merge. Log rotation keeps a rolling window per run without data loss: when the stored entries exceed the reviewed max entries, the overflow moves to the reviewed overflow target store (recorded as a rotation target with its overflow entry count) while the newest window stays live, so the sum of kept and rotated entries always equals the captured total. Level filtering is severity ranking: every level of the reviewed level set carries a severity rank and a per step level floor drops every entry more verbose than the floor, source filters drop entries from sources outside the reviewed grammar, and the console capture applies the floor before an entry ever leaves the page bridge. The console diff between two runs classifies each line by multiset comparison: lines the target run carries beyond the base count classify as added, lines the base run carries beyond the target count as removed, and the shared minimum of each line classifies as repeated with its repeat count. The blocking duration of a step window is the sum of the long task durations that started inside the window, with entries below the reviewed threshold excluded before the sum.

## Session memory arithmetic since 1.1.49

Task state is checksum arithmetic: the checkpoint hashes the run id, step cursor and recorded output lengths into one stable local checksum, a resume recomputes the checksum over the stored payload and a mismatch refuses the resume, and the crash detector marks a run interrupted when the browser restarts before the cursor reaches the end of the plan. Capture is section arithmetic: the reviewed snapshot plan toggles tabs, scroll, forms, storage and cookies per user choice, every tab keeps its url, title, index, scroll position and non password form state, and the local storage pairs and cookie names join the record only for granted origins. ## Run lifecycle state machine (1.1.70)

The local first arithmetic keeps the page data on the device: `localfirst` processes every extraction before any export — the extractapi replay executor runs its mapped fields through the pass so nothing leaves the page boundary unstripped — holding the extraction, the aggregation and the diffing on the device, stripping the identity fields the reviewed plan never listed (an email, phone, name, address, account, session, user, ip, location, cookie or token shaped field holds only when the review named it) and holding the localrule fields of the origin always, because a field the user marked local never leaves the device for any review; the `localgate` refuses any outbound payload that carries a local rule field at every boundary and the `minimizationstripgrade` grades an extraction clean only when every field sits inside the reviewed set.

The posture arithmetic fixes the counters and the sync. `notelemetry` keeps every counter inside the local memory: the telemetrypolicy type fixes the enabled literal to false so an on state is unrepresentable by construction, the background worker issues no outbound usage call from any context, and the protocol requestbody omits every telemetry field by construction — no telemetry key exists on the wire format at all, so the invariant holds at the schema level instead of an omission at runtime. `optinsync` stays disabled until the user lists every data class and turns each one on: runs, memory, captures, settings and provenance opt in per class with the consent stamp of each enablement recorded for the audit trail, a class the listing never offered never enables, and the `syncgate` requires the opt in flag before any sync transport fires. `encryptsync` derives the key from the user passphrase through the key derivation seam (the executor wires the webcrypto PBKDF2 pass while the passphrase itself never persists and never rides a payload), encrypts every payload through the cipher seam before the transport, stamps the format version tag, and refuses a sync without the passphrase — a passphrase the user never typed never defaults in code — while the `encryptsyncgate` refuses plaintext payloads and the syncpass composes the whole pass with the payload hash recorded in the syncrecord.

The lifecycle arithmetic answers the user requests. `purgeonrequest` deletes the stored data by scope on the user request: the data inventory lists every stored key with its class and size, the full scope demands the typed confirmation phrase under the `purgegate`, the audit class never deletes because the immutable audit hashes survive every purge, and every deleted key enters the audit trail. `exportall` bundles every stored record — the runs, the memory items, the captures, the settings and the provenance entries — into one portable file on the explicit user action under the `exportallgate`, and `streambundle` walks the bundle in chunks of the explicit size with no cap because a bundle the user asked for streams whole. The cookie jar arithmetic isolates every task: `newjar` assigns one jar per task run at the run open, `jarscope` binds every cookie read and write to the active jar under the `jargate` (a sealed jar refuses every write), `sealjar` seals the jar at the run completion under the user expiry window so the automatic expiry pass clears the expired entries while the jar record stays, and `cleanupafterrun` clears the task artifacts of a completed run under the user cleanup schedule while the artifacts flagged for retention stay and the `cleanupgate` never deletes the audit history without consent. `enforcequarantine` holds every download in the sandbox folder until the scanner verdict arrives — the `quarantineopengate` blocks opening a file without a clean verdict, the `scannerhookgate` keeps the verdicts on the user configured scanner endpoints, a clean verdict releases, a flagged verdict deletes and a pending or error verdict holds because a hook failure never releases anything.

## Bridge review flow (1.1.82)

The bridge review flow extends the approval gate family to the site: when a run proposes a plan while the bridge is paired, the extension composes the review card (the proposal id, the plan title, the steps with their kinds, origins and sensitive marks) and posts it as a planproposal event; the chatbridge widget on the site renders the card, the site reviewer answers with the planreview event (the decision, the reviewer name and the note), and the extension review gate consumes exactly the decisions its own approval flow accepts — the sensitive steps still approve only through the extension approval flow, the site never executes anything, and the offline queue buffers the review requests while the socket is down with the replay deduplication on reconnect so a dropped decision never double applies. The bridge audit events record every operation with the session id, the heartbeat frames keep the socket alive during long runs under the user interval, and the idle window expires the quiet sessions.

## Model provider gateways (1.1.83)

The gateway layer makes the agent reachable from any model provider through one adapter contract: the openaicompat adapter speaks the chat completions shape with any compatible endpoint the user configures and streams the response deltas as they arrive, the anthropicgateway adapter speaks the messages shape with streamed content blocks and the system prompt mapped to the provider format, the geminigateway adapter speaks the generate content shape with streamed candidate parts and the tool schemas mapped to the function declarations format, and the ollamalocal adapter speaks to a localhost endpoint that defaults to the local machine and never to a cloud url, listing the locally installed models. Every adapter shares one request, stream and cancel contract: the dispatch loop runs the consent and base url gates first, races the timeout, retries the transient failures under the jittered backoff, honors the retry-after header of the 429 answer with its announced window, maps the 401 and 403 answers to the unauthorized error the vault rotation answers, and the cancel state stops before the dispatch and between the attempts.

Nothing is hardcoded: no remote endpoint, no model name and no key ever leaves the user configuration — the baseurlconfig validates the scheme, host and path shape before saving (a query or fragment refuses, a relative path segment refuses, the remote providers must speak https, and the ollamalocal adapter accepts localhost hosts only), the keys live in the keyvault behind the storeproviderkey, resolveproviderkey and revokeproviderkey seams (the key material resolves at the last possible moment, the requests mask before any log, and the keyexportcheck refuses any export that carries a key shape), and every timeout, retry count, backoff base, jitter window and cache window stays a user choice with no code default. The modellist discovery caches under the user window, the capabilityad advertisement serializes the tool catalog into the provider specific schema with the consent metadata and the plan review gate riding the required capabilities — a model answer never executes a step the human review did not approve — and the resolvegatewayroute resolution maps each task kind onto its provider and model through the user routing table with the fallback pair and the local provider standing in when the gates refuse the remote calls. The budget tracking rides the same costbudget gate the llm family already runs (the usage records carry the local marker for the calls that never left the machine, the cost estimates answer the user configured price per million tokens), and the guardrails wrap every parsed response: the gatewayguard caps the parse attempts with its retry prompt, the guardretryprompt names exactly what the retry asks, and a response that never parses answers the structured gateway error instead of leaking through.

## The approval gate for remote callers (1.1.84)

The approval gate flow extends to the remote callers of the mcp server mode: when a client calls a sensitive tool, the call context blocks in flight, the approval request renders in the sidepanel with the caller identity and its intent, and the call proceeds exactly when the human answers — never on a timeout, never in a batch. The consent requirements refuse execution when the grant is missing, the dry run mode executes without side effects, the idempotency keys deduplicate the repeated calls so a retried request never double applies its effect, and every call writes its audit entry with the caller, the tool and the outcome. The server degrades to read only tools when no origin grant exists, the client allowlist and the per client rate caps hold the boundary, and the shutdown drains the in flight calls before the exit so no approval ever loses its answer.
