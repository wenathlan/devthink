# Library modes (1.1.67)

The library modes are the consumption surfaces of the 1.1.67 ecosystem part two family, recorded here as the roadmap item 99 promised: one source tree builds the esm, cjs and umd bundles, the node, bun and deno runtime entries load them, the package.json exports map routes every consumer, and the declaration files derive from the source with no hand written drift. No mode widens anything: every runtime speaks the same protocol, runs the same policy engine and keeps the same consent gates the extension runs, and the terminal surface beside these modes (planlint, flowrun, exporttools, headlesslib) is documented in docs/20.workflowlibrary.md.

## the runtime matrix

The matrix declares itself in one place — `platformtargets()` of the runtime module — and the build matrix run compiles every declared target from the shared core, so a runtime enters through one declaration and never through scattered build flags:

| Runtime | Entry | Dist bundle | Format | Platform | Mode |
| --- | --- | --- | --- | --- | --- |
| browser | `umd.ts` | `dist/devthink.umd.js` | umd | browser | umd |
| node | `node.ts` | `dist/node.cjs` | cjs | node | cjs |
| bun | `bun.ts` | `dist/bun.js` | esm | node | esm |
| deno | `deno.ts` | `dist/deno.js` | esm | neutral | esm |

The browser target serves script tag consumers under the product name `devthink.umd.js` with the lowercase `devthink` global, the node target serves require consumers through its cjs shell, and the bun and deno targets ride the esm core entries of their runtime shells. Every target ships its minified variant beside it (`devthink.umd.min.js`, `node.min.cjs`, `bun.min.js`, `deno.min.js`) with its sourcemap, the version stamp and the license banner, one checksum line per target in `dist/checksums.txt`, and the bundle size accounting fails an oversized bundle before it ships. The `matrixverify` check walks the declared targets against the built entries so a missing runtime fails the matrix run.

The root entry carries the browser condition that selects the neutral target — the browser platform build strips every node import because the whole core reaches the platform through the adapter seam — while the import, require and default conditions serve the esm and cjs cores. The per-module entries ship the policy, protocol, memory and progress families as their own tree shakable bundles (the hardening and dashdone families ship the same way beside them), so a consumer imports a single family without touching the frozen index surface.

## the dist bundles

The build emits the core as `dist/index.js` (esm), `dist/index.cjs` (the cjs entry wrapped behind the stable getter object so require consumers read the same named exports the esm mode reads), `dist/index.neutral.js` (the browser condition target) and `dist/devthink.umd.js` (the script tag bundle); the runtime shells as `dist/node.cjs`, `dist/bun.js` and `dist/deno.js`; the per-module entries as `dist/policy.js`, `dist/protocol.js`, `dist/memory.js` and `dist/progress.js` beside `dist/hardening.js` and `dist/dashdone.js`; and the terminal, protocol and tooling entries as `dist/cli.js`, `dist/headless.js`, `dist/mcp.js`, `dist/bridge.js`, `dist/companion.js`, `dist/gateway.js`, `dist/crossbrowser.js`, `dist/pack.js` and `dist/http.js` — every target with its minified variant, its sourcemap, the version stamp and the license banner, and one checksums line per target in `dist/checksums.txt`.

## the engines

The engines field declares the bounded runtime ranges the package supports: `node >=26.8.1 <27`, `npm >=12.0.2 <13`, `bun >=1.4.0 <2` and `deno >=2.0.0 <3`, with `pnpm@11.24.0` as the canonical lockfile tool through the packageManager field. Node, npm and bun carry dedicated bounded compatibility declarations the release pipeline checks; the maintenance workflow refreshes the version catalog of docs/runtimeversions.md after each release.

## the declaration files

The declaration files derive from the source with no hand written drift: the build runs the typescript compiler over `tsconfig.build.json` and emits one declaration file (and its map) for every entry point of the matrix, the per-module entries, the terminal entries and the runtime adapters — index, cjs, neutral, policy, protocol, memory, progress, hardening, dashdone, types, runtime, umd, node, bun, deno, headless, cli, agent, auth, http, gateway, page, mcp, serve, tools, bridge, crossbrowser, pack, companion and version. The declaration bundle ships as its own release artifact (`devthink-declarations-<version>.zip`) beside the umd bundle.

## one import per runtime

One example per runtime lives in the repository under `tests/code` (`bun.ts`, `cjs.js`, `deno.ts` and `umd.html`), the build copies the runtime examples into `dist/fixtures`, and the umd example ships as `dist/umd-example.html` with its bundle reference rewritten to the dist root.

node with require (the cjs mode, the stable getter object):

```js
const devthink = require("@wenathlan/extension");

const stamp = devthink.bundlestamp();
console.log(`devthink ${stamp.version} in ${stamp.mode} mode`);
console.log(`policy exports ${Object.keys(require("@wenathlan/extension/policy")).length} functions`);
```

bun with import (the esm mode under the node default adapters):

```ts
import { bundlestamp, parseproposal } from "@wenathlan/extension";

const stamp = bundlestamp();
console.log(`devthink ${stamp.version} in ${stamp.mode} mode under bun ${Bun.version}`);
```

deno with npm specifiers (the deno adapter reads its configuration through the deno runtime permissions the deno.json compatibility map declares):

```ts
import { bundlestamp, platformtargets } from "@wenathlan/extension";

const stamp = bundlestamp();
console.log(`devthink ${stamp.version} in ${stamp.mode} mode under deno ${Deno.version.deno}`);
console.log(`the platform matrix covers ${platformtargets().length} runtime targets`);
```

the browser with a script tag (the umd mode exposes the lowercase `devthink` global only):

```html
<script src="./devthink.umd.js"></script>
<script>
  const out = document.getElementById("out");
  out.textContent = JSON.stringify(window.devthink.bundlestamp(), null, 2);
</script>
```

## the adapter seam and the mode stamp

Every platform primitive flows through one adapter contract: the storage, clock, logger and fetch adapters, with the node default composition binding the filesystem, the browser default composition binding the chrome storage area (an absent area falls back to the in-memory store, so the script tag bundle runs with no chrome api present) and the deno default composition binding the kv store the deno host opened. No binding is hardcoded — the node bindings arrive as injected filesystem primitives and the deno bindings as an injected kv store, so the neutral and browser bundles never carry a node import. The shared adapter registry lives on the global symbol registry (`Symbol.for`), so the esm and cjs modes of one process read one active adapter instead of forking the dual package hazard, and `bundlestamp()` answers the version, the consumption mode and the dist target of the bundle the caller loaded — each dist entry stamps itself once at load. The capability probes detect dom, storage, network and worker availability per runtime and downgrade the features a runtime lacks with their reasons instead of failing the runtime; a runtime that probes the dom executes every reviewed kind the vocabulary declares, and a runtime without one executes the kinds its domless filter admits.

## the verification lanes

The verify workflow runs the multi runtime matrix: a require smoke against `dist/index.cjs`, an import smoke against `dist/index.js`, a global smoke against `dist/devthink.umd.js`, a deno check over the deno entry and the vitest suite once under bun. The library modes suite of `tests/librarymodes.test.ts` builds every platform target of the matrix in one run and loads each bundle, keeps the deno entry free of node shims, covers the cjs getter object, the adapter probes per platform, the declaration emission for every entry point and the build matrix across all platform targets.
